# 第 11 章 项目与模块

<!-- LANGUAGE NAVIGATION -->
[English](en/11-modules-projects.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

程序变大以后，入口、业务模块、配置和运行资源需要各自明确的位置。模块决定声明的归属与查找，工程配置决定编译输入与输出，工作目录又影响应用读取文件；三者相互配合，但职责不同。

本章从目录与限定名开始，说明如何记录可复现的工程边界，并解释标准库内嵌核心资产与用户项目的关系。目标是让项目离开当前开发目录以后，仍能说明需要哪些输入和依赖。

## 11.1 先确定入口和目录

先为工程确定一个明确入口，再把与它协作的代码按职责放进模块。可以从 src/main.chl 启动，把 HTTP、业务与存取逻辑分别组织，而不是让每个文件都同时承担所有工作。

网页、配置等资源另有运行期路径。import 能找到源码，只证明编译输入可用；应用读取相对文件时还依赖启动目录。把这两个路径问题在目录设计时分开记录，部署时就少一层猜测。

顶层的普通全局变量只在声明它的模块中使用。供其他模块读取的值可以声明为模块常量，例如 `const int64 DEFAULT_PORT = 8080;`。导入方可用 `config::DEFAULT_PORT`，语言服务提供补全、悬停和定义跳转。声明前的文档注释会出现在悬停中。

## 11.2 模块声明与限定名

模块声明为名称提供归属。import 引入所需模块，限定名用于明确选择声明，尤其在多个模块出现同名类型时。不要依靠某一轮导入顺序解决重名；写出限定名并让诊断暴露真正冲突。

导入模块后，名称能够唯一确定时，函数、常量、接口、枚举和结构体等声明都可以直接使用短名，规则不限于函数。前面的模块常量也可以写 DEFAULT_PORT；需要消除重名时才写 config::DEFAULT_PORT。泛型函数的类型实参也可继续省略，但模块归属与类型推断分别检查：短名唯一不代表每一种实参类型都合法。

<!-- verify-book -->
```chali
inline int64 square(int64 value)
{
    return value * value;
}

void main()
{
    println("{}", square(3));
}
```

```text
9
```

square 声明一个接收 int64、返回 int64 的普通函数，计算 value*value；main 传入 3 后得到 9。inline 是编译相关标记，不改变参数传递和返回值的语义，也不能单靠这个标记证明实际机器码已经内联。

这段例程完整可运行，但没有 module 或 import，因此只用于说明可放入模块中的函数声明，不能据此认为已经演示了多文件搜索与可见性。拆到真实工程时，还要核对模块归属、限定名和源码路径；计算结果与模块组织是不同层次的问题。


## 11.3 项目配置与命令

chali.toml 保存入口和项目选项。打开现有工程时，可用 chali help 对照当前支持的配置。run 采用 checked AOT，发布构建原生产物。工具链路径、目标信息和链接资产见第 27 章。


### 一份可以保存到工程根目录的清单

使用 `chali new demo` 可以生成目录和清单。已有工程可在根目录创建 `chali.toml`：

```toml
[package]
name = "demo"
version = "0.1.0"

[chali]
main = "src/main.chl"
search_paths = ["src"]

[build]
build_option = ["A", "B"]
output = "executable"
lto = "full"
allocator = "malloc"
```

`[package]` 记录包的名称和版本；`[chali]` 指定入口和源码搜索目录；`[build]` 保存目标产物及构建选项。相对路径以清单所在目录为基准。编译器从显式源文件所在目录向上寻找 `chali.toml`；没有显式源文件时，从当前工作目录向上寻找。找不到清单时使用单文件默认配置。显式源文件会取代 `main` 入口，仍读取它所属工程的配置。

在工程根目录执行：

```sh
chali check
chali run
chali build
chali run -B EXTRA
```

前三条命令使用 `main` 指定的入口；最后一条额外定义 `EXTRA`。清单中的 `A`、`B` 和命令行中的 `EXTRA` 都可以用 `$build[A]`、`$build["B"]`、`$build[EXTRA]` 查询，未定义名称得到 `false`。这些选项只表示布尔存在性，不携带数值，也不支持通过 `false` 取消清单中的定义。第 22 章介绍如何在宏模板的 `$if` 中使用它们。

`search_paths` 同时补充模块与导入搜索目录；需要分别配置时，可在 `[chali]` 使用 `include_paths` 和 `import_paths` 数组。命令行 `-I`、`--include-path`、`--import-dir` 仍用于目录，`-B` 用于布尔标志。目录搜索项追加；标志名称取并集。目标、输出及链接设置的覆盖规则见第 27 章，不要把所有配置都理解成同一种合并方式。

### 标准库为什么可以随编译器一起交付

理解标准库时，要区分源码、预编译的前端表示和最终机器代码。源码适合阅读、诊断和导出；前端表示保存编译器已经识别的声明与语法结构；机器代码则与具体目标和实例化结果有关。把其中一层放进编译器，并不意味着后面所有工作都已完成。

当前 1.0.0 将 std::core 核心、可选标准模块和模板目录作为二进制资产编入编译器。导入模块时，编译器在进程内按需恢复解析节点和模板定义，并核对格式、源码身份与内容摘要。发行编译器不需要到原来的 build 目录寻找这些资产，默认也不读写磁盘标准库缓存。

具体类型的泛型实例化、宏调用的展开、用户程序的检查和目标代码生成仍需进行。例如，`List<int64>` 与 `List<String>` 共享内嵌的模板定义，各自的类型检查和目标代码生成仍由当前编译完成。这里保存的是可重定位的前端表示；它不会把某个目标平台的容器机器代码直接搬到另一个平台。源码仍随编译器保留，用于阅读、诊断、导出以及需要时的解析回退。

标准库内嵌资产、用户工程的增量结果和应用运行期资源各有用途。复制编译器不等于复制网页、配置和数据库；删除工程缓存也不应成为修复标准库资产损坏的办法。遇到问题时，先区分是编译器资产装载、用户模块解析还是应用资源读取失败，再处理对应层次。

资产格式、源码回退及项目增量检查的具体选项见[工具链说明](../09-toolchain.md)。

## 11.4 可复现的工程边界

在 README 记录启动目录、外部库、数据文件和目标平台。在 CI 中分开检查类型、运行例程与打包产物；生成文件从生成源维护，不通过编辑产物修补下一次必然被覆盖的内容。

### 在源码中声明模块

单文件也可以有模块名，并用限定名调用模块内函数。

<!-- verify-book -->
```chali
module book_demo;

int64 answer() {
    return 42;
}
void main() {
    println("{}", book_demo::answer());
}
```

```text
42
```

### 小结

将编译时需要的源码、编译器自带的资产与应用运行时需要的文件分别记录。模块导入成功不代表网页路径正确，编译器能恢复核心标准库也不代表可选模块和用户泛型都已变成机器代码。

可复现说明应包含入口、配置位置、启动目录、目标与外部库。后面讨论宏与反射时，名称来源和类型归属仍按这些工程边界处理，不会因生成代码而消失。

## 11.6 番外：两个李逵，一个名字

改写自《水浒传》李逵遇李鬼一节。

李逵行至岭边，跳出一个黑大汉，抡着两柄板斧，喝道：“留下买路钱！俺是黑旋风李逵！”李逵听得大怒，喝问：“你既是李逵，俺又是谁？”

二人争得面红耳赤，驿站伙计却只认短名，差点把工钱给了李鬼。掌柜拦住道：“名字相同，未必来自同一模块。且把限定名写全。”李逵写梁山，李鬼写树林，事情顿时清楚了许多。

李鬼又哭诉家有九十岁老母，声称自己只是一个本地同名声明，愿意遮蔽一下，绝不影响外部接口。李逵一时心软，许他暂留。回头再查，果见那厮在屋中商议如何冒领整个包的导出。

李逵一斧劈下，骂道：“遮蔽是名称解析的规矩，不是冒领的许可证！”

掌柜从此导入必查路径，同名必写归属。伙计问：“未声明模块者如何？”掌柜道：“记入小写 `program`，莫给它擅加一个大写头衔。”

李逵听罢，仍嫌字多。直到月底领钱，见收据上清清楚楚只付给梁山那位，才夸这套限定名虽不如板斧爽快，倒确实少一场人命官司。

### 技术对照

模块名、文件搜索路径和符号名称共同决定解析。唯一短名便于调用，同名冲突时使用限定名；本地声明的遮蔽也需要明确检查。
