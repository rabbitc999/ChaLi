# 第 9 章 资源与作用域

<!-- LANGUAGE NAVIGATION -->
[English](en/09-resources-scopes.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

文件、连接与缓冲区除了保存数据，还承担关闭或释放责任。写出“何时取得资源”以后，还要说清谁拥有它、何时交出它、每条退出路径由谁清理。

本章先让退出动作打印消息，观察登记与执行的区别，再用 Closeable 资源跟踪移动后的拥有者。理解自动清理后，最后才讨论需要显式协议的手动分配，避免把不同接口混作一种释放方式。

## 9.1 先看一对大括号

<!-- verify-book -->
```chali
void main()
{
    int64 outer = 1;
    {
        int64 inner = 2;
        println("里面能看到 {} 和 {}", outer, inner);
    }
    println("外面只剩 {}", outer);
}
```

```text
里面能看到 1 和 2
外面只剩 1
```

outer 声明在 main 中，内部块可以读取它。inner 只在嵌套块里有效，因此第一条输出能读到两个名字，离开那对大括号后只使用 outer。把最后一条改成读取 inner，应在编译时失败。后面让变量拥有资源时，也从这些进入和离开作用域的位置判断清理。

## 9.2 离开作用域时的动作

先不打开真实文件，只用打印观察“离开这个块时做一件事”。defer 记录一个退出动作，scope(exit) 可以记录一段代码。登记时程序继续向下走，直到实际退出这个作用域才执行它们。

如果登记多个动作，就按逆序执行。这与处理层层取得的资源很相称：后来取得的依赖通常先撤销。提前返回或退出循环也会经过相应作用域的清理路径，不能只检查花括号自然结束的情况。

<!-- verify-book -->
```chali
void main()
{
    {
        defer println("first");
        scope (exit)
        {
            println("second");
        }
        println("body");
    }
}
```

```text
body
second
first
```

进入内层花括号时，defer 登记 first，scope(exit) 随后登记 second；登记清理动作不会立即打印它们。程序先执行普通语句，所以第一行是 body。

离开这个块时按逆登记顺序执行退出动作，先 second，再 first。外层 main 的花括号与这里的清理范围不同；如果把登记位置移到外层，执行时机也会改变。读资源代码时，可以在每个块边界列出已登记动作，再倒序核对退出路径。


## 9.3 Drop 与字段清理

实现 Drop 的值可以在 drop 方法中处理自己的资源；随后按类型规则清理拥有字段。drop 中不转移或显式释放 self 本身。含引用字段的值不因此拥有引用目标，清理该值也不等同于释放借用来源。

复制具有清理行为的值时，还需判断类型是否允许复制，以及副本各自拥有的资源。把资源句柄按整数复制并不能建立两个独立拥有者。

## 9.4 Closeable 与所有权转移

Closeable 表达关闭协议，实现它的结构体按不可复制资源处理。需要把资源交给另一个拥有者时使用相应移动规则；借用时保持来源存活。下例观察资源消费与关闭次序，关注拥有者而不是整数 id 的数值。

<!-- verify-book -->
```chali
struct Handle : Closeable
{
    int64 id;

    void close()
    {
        println("close {}", self.id);
    }
};

void consume(Handle handle)
{
    println("consume {}", handle.id);
}

void main()
{
    Handle first;
    first.id = 1;
    consume(move first);

    Handle second;
    second.id = 2;
    Handle third = move second;
    println("third={}", third.id);
}
```

```text
consume 1
close 1
third=2
close 2
```

Handle 实现 Closeable，close 通过打印 id 显示资源清理发生的时间。first 的 id 设为 1 后，`consume(move first)` 把所有权交给函数形参；consume 先打印消费信息，返回时由该拥有者关闭资源 1，调用方不能继续使用 first。

second 的资源 2 随后移动给 third，移动不会额外产生一个需要独立关闭的副本。打印 third 的 id 后，到 main 作用域退出时才关闭资源 2。因此输出顺序对应“消费 1、关闭 1、观察 2、关闭 2”。close 的打印只是示范可观察生命周期，真实句柄还应在其中释放各自的外部资源。


## 9.5 手动分配的边界

new T 创建手动分配的存储，带构造参数时写 new T(args)。这与普通局部拥有值的作用域清理不是同一个接口：按对应所有权协议释放，不把裸存储误认为自动资源包装。

关闭、移动和释放会影响借用。已知的终结路径可能被编译器合并，但不应用重复释放来推断任意指针安全。原始存储、unsafe 与存活检查在第 25 章展开。

### 小结

资源追踪可以维护两份记录：当前作用域登记了哪些退出动作，当前哪个值拥有每项资源。move 改变后一份记录，离开作用域触发前一份及拥有值清理；引用本身不接管被借用资源。

不要用“最终没有崩溃”证明关闭正确。用顺序、拥有者和实际结果核对正常退出与提前返回；不安全存储中的逐槽初始化与清理则留到第 25 章。

## 9.6 习题

1. 解释示例中 second 在 first 前输出。
2. 含引用字段的值是否拥有来源？
3. Closeable 值如何交给新拥有者？
4. 比较局部值与 new 存储的清理接口。

### 参考解答与验收要点

1. 退出动作按注册逆序执行。
2. 不拥有；来源需按自己的寿命规则管理。
3. 使用合法移动，并停止使用已移动的原绑定。
4. 局部拥有值按作用域清理，手动存储按相应释放协议处理。

## 9.7 番外：出了作用域的穿墙术

改写自《聊斋志异·劳山道士》。

邑有王生，慕仙道，负笈至劳山。道士授以一钥，曰：“此乃借用，室在则可用，室闭则当还。”生受教，练习数月，未曾读过一行生命周期说明。

一日辞归，求穿墙之术。道士曰：“汝将出作用域，室中器物不可随身。”生拍囊笑曰：“器物未取，位置已记，岂不轻省？”道士但笑，不复言。

归家，夸于妻曰：“我已学成零成本访问，虽隔千里，伸手可得。”妻不信，令试之。王生面壁，念念有词，将旧地址向前一送，只听砰然有声，额上坟起，如巨卵焉。

妻笑曰：“你那口诀，莫非叫无效句柄？”生怒，欲将借用改为拥有，发现构造函数不肯签字；又想再释放一次，池子也不肯。

道士后闻之，曰：“我早告汝，记住坐标，不等于买下房产。人既走出山门，莫拿昔日工位当永久服务器。”

王生于是将旧钥挂于壁，题曰“性能优化纪念”。每有客来，先说自己已学会安全编程，再请客人不要碰额头，尚在增量恢复。

### 技术对照

作用域结束、显式关闭和拥有关系转移会影响资源可用性。析构协议只处理由当前对象负责的资源；裸内存与宿主句柄仍需遵守各自接口约定。
