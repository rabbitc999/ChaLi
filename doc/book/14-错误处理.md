# 第 14 章 错误处理

<!-- LANGUAGE NAVIGATION -->
[English](en/14-error-handling.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

查找可能没有结果，读取文件可能失败。用零或空字符串表示所有情况，会和合法数据混在一起。Option 描述有没有值，Result 描述成功还是失败；先在调用者手里把两条路径分清楚。

## 14.1 查找不到也是一种结果

<!-- verify-book -->
```chali
Option<int64> findFirst(List<int64> xs, int64 target)
{
    for (int64 x in xs)
    {
        if (x == target)
        {
            return Value(x);
        }
    }
    return None;
}

void main()
{
    List<int64> xs;
    xs.push(3);
    xs.push(7);
    println("{}", findFirst(xs, 7).unwrap());
    println("{}", findFirst(xs, 9).unwrapOr(-1));
    match (findFirst(xs, 3))
    {
        Value(v) => { println("found = {}", v); }
        None => { println("no"); }
    }
}
```

```text
7
-1
found = 3
```

findFirst 逐项比较。找到就用 Value(x) 返回，没找到才走末尾的 None。返回的不是一个约定的特殊整数，而是带状态的值。

main 的第一条查询确实存在 7，因此 unwrap 得到 7。第二条找不到 9，unwrapOr(-1) 明确选择后备值。第三条 match 展开两种情况，只在 Value 分支中读取载荷。unwrap 在缺失时会失败，不能用它替代“是否存在”的判断。

## 14.2 成功与失败都带上需要的数据

<!-- verify-book -->
```chali
Result<int64, Error> checkedScore(int64 value)
{
    if (value < 0 || value > 100)
    {
        return Result<int64, Error>::Err(MessageError::from("invalid score"));
    }
    return Result<int64, Error>::Ok(value);
}

Result<int64, Error> addBonus(int64 value)
{
    int64 score = checkedScore(value)?;
    return Result<int64, Error>::Ok(score + 5);
}

void main()
{
    match (addBonus(70))
    {
        Ok(score) => { println("{}", score); }
        Err(error) => { println("{}", error.toString()); }
    }
    match (addBonus(-1))
    {
        Ok(score) => { println("{}", score); }
        Err(error) => { println("{}", error.toString()); }
    }
}
```

```text
75
invalid score
```

先读 checkedScore。参数位于 0 到 100 时返回 Ok(value)，否则创建有说明文字的 MessageError，作为 Error 交给 Err。Error 提供统一的 toString 显示接口；怎样保留并区分具体错误，第 17 章再展开。

再看 main 的两个 match。70 通过校验，得到加分后的 75；-1 进入 Err 分支，打印 invalid score。相同的调用结果类型，要求使用者明确面对两种状态。这里的错误文字不是成功载荷，也不应伪装成一个合法分数。

## 14.3 用问号把不能继续的状态交回去

addBonus 中的 checkedScore(value)? 先看状态。Ok 时取出整数交给 score，继续下一条语句；Err 时立即从 addBonus 返回错误，不执行加 5。

? 没有消除错误，也不会自动重试。它只是把处理决定交给上一层；本例由 main 负责显示。它必须处于兼容的返回类型中，不能在返回 void 的 main 里随意传播一个 Result。Option 的 ? 则在 None 时按缺失协议提前返回。

提前返回仍执行已经建立的作用域清理。因此把资源获取、读取与返回组合时，既要检查错误如何传播，也要看文件句柄由谁拥有。

## 14.4 在能做决定的位置恢复

库函数返回 Result，让调用者选择重试、提示用户或终止。命令行入口可以报告失败；交互界面可以让用户改正输入。不要在底层把所有失败改成空列表，否则上层无法区分“没有匹配”和“文件打不开”。

日志项目会给文件错误补上路径，再交给入口输出。需要按具体 IoError 实现分支、多载荷模式或自定义 Try 时，继续读第 17、18 章；先掌握这里的成功、失败与提前返回就能完成下一个项目。

## 14.5 习题

1. findFirst 找不到元素时返回什么？
2. unwrapOr(-1) 是否把 -1 存入了原 Option？
3. addBonus(-1) 是否执行了加 5？
4. 为什么库函数不把读取失败改成空字符串？

### 参考解答与验收要点

1. None，与找到整数 0 等正常值区分。
2. 没有，它是本次读取的后备值。
3. 没有，? 提前传播 Err。
4. 需要保留合法空内容与失败的区别，让调用者决定恢复方式。

## 14.6 番外：错误又来了

改写自伊索寓言《狼来了》。

一个放羊的孩子在山坡上看羊，觉得空闲无聊，便向村里大喊：“成功了！成功了！”村人赶来，才发现网络已经断了，返回值只是孩子随手填的零。

第二天，孩子又喊成功。村人问查询结果，孩子答：“零只羊。”问是不是空集合，答：“也许。”问是不是没有对象，答：“也许。”问是不是操作失败，孩子拍着终端道：“反正没有错误，错误都被我改成零了。”

村人渐渐不再看他的报信。到了狼真来时，警报查询恰好失败。孩子照例送回零，仓库照例撤销警报。羊群照例遭殃，只有监控图表一片安宁。

老村长气得胡子直抖，给孩子订了规矩：成功就带数，未找到就说未找到，失败就带具体错误。别让 `Option`、`Result` 和零值三家挤在一个门牌下。

孩子问：“那么传给上一层之后，狼是不是就走了？”村长说：“`?` 是传话，不是驱狼。上层还得决定重试、求援还是撤离。”

后来村里每个错误都实现了同一个 `Error` 接口，却仍保留各自的细节。狼又来时，孩子终于能说清是哪一路失败。村长颇欣慰，只叮嘱一句：“别为了报表好看，又给我统一成‘未知异常’。”

### 技术对照

Option 表达存在与否，Result 表达成功或失败。错误传播不等于已经恢复；unwrap、assert 和 panic 适合的前提需要由调用位置明确保证。
