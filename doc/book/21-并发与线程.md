# 第 21 章 并发与线程

<!-- LANGUAGE NAVIGATION -->
[English](en/21-concurrency.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

日志工具按顺序做完一项工作再做下一项。若两项工作彼此独立，可以创建线程；若工作主要在等网络输入，也可以在一个线程里轮流推进多个连接。这两种做法需要管理的资源不同，本章先把线程的开始、通信和结束写清楚。

## 21.1 创建一项任务并等待

<!-- verify-book -->
```chali
import std::thread;

void worker()
{
    println("worker");
}

void main()
{
    Thread task = create(worker);
    wait(task);
    println("done");
}
```

```text
worker
done
```

import 引入线程模块。worker 是不接收参数的静态任务入口；这里只输出一行，先不引入共享数据。

main 的第一条语句创建任务并保存句柄。线程可能在 create 返回前后开始执行，不要根据源码位置猜调度顺序。下一条 wait 等待它结束，所以 done 一定在 worker 的输出后出现。等待完成也回收任务的等待责任，不能对同一句柄重复等待。

如果删掉 wait，只能说 main 不再主动等待这项任务，不能继续把两行的顺序当成约定。并发例子中的预期输出必须由同步操作保证。

## 21.2 给任务一份初始数据

<!-- verify-book -->
```chali
import std::thread;

void report(int64 score)
{
    println("score:{}", score);
}

void main()
{
    int64 score = 70;
    Thread task = createWith(report, score);
    score = 90;
    wait(task);
    println("main:{}", score);
}
```

```text
score:70
main:90
```

report 的参数属于任务自己。createWith 在创建时传递一份符合复制规则的初始值，接着主线程把本地 score 改为 90，不会改变任务收到的 70。

wait 再次建立输出顺序。不要把 &score 或文件、套接字、借用闭包当作可随意复制的初始数据；线程运行在隔离上下文中，入口与参数必须符合跨线程传递规则。想传一个包含多个值的配置，可以先定义可复制的结构体。

## 21.3 用消息建立先后关系

<!-- verify-book -->
```chali
import std::thread;

void receiver()
{
    String message = receive();
    println("received:{}", message);
}

void main()
{
    Thread task = create(receiver);
    send(task, "ready");
    wait(task);
    println("joined");
}
```

```text
received:ready
joined
```

receiver 在 receive 处等待自己的收件箱，不轮询主线程变量。main 用任务句柄把 ready 发送给它；消息准备好以后，receive 返回 String，任务输出并结束。最后 wait 确认完成，才输出 joined。

这里的消息内容就是一份明确的输入。多个消息还需要约定怎样表示结束，例如单独的结束消息或关闭通道。发送一个空字符串和关闭通道不是同一件事。需要有类型的消息和关闭状态时，使用 `std::concurrency::Channel<T>`，签名见标准库参考。

### 用条件交换认领共享状态

`AtomicInt64::create(0)` 创建共享整数槽。通过 `createWith` 传递句柄时，任务仍访问同一个槽。`compareExchange(expected, desired)` 把比较和写入合成一次原子操作。值与 `expected` 相等时写入 `desired` 并返回 `true`，否则返回 `false`。如果先 `get()` 再 `set()`，其他线程就能在两次调用之间认领同一份工作。

下面用 `0` 表示尚未认领，`1` 和 `2` 分别表示两个任务。主线程用通道收集两次交换结果，用 `wait` 确认任务结束。任务调度决定谁赢，因此只验证成功的次数和共享槽的最终取值范围。

一次条件交换只保护这个整数槽。如果成功后还要更新其他字段，那些更新需要自己的同步协议。把失败当作「这次没有取得状态」，根据协议退出、重新读取或重试。如果状态允许从 `0` 变成其他值再回到 `0`，条件交换只能比较当前值，无法知道中间是否被修改过。

<!-- verify-book -->
```chali
import std::concurrency;
import std::thread;

struct Claim {
    AtomicInt64 state;
    Channel<bool> outcomes;
    int64 id;
};

void claim(Claim job) {
    bool won = job.state.compareExchange(0, job.id);
    assert(job.outcomes.send(won) == READY);
}

void main() {
    Claim job;
    job.state = AtomicInt64::create(0);
    job.outcomes = Channel<bool>::create(2);
    job.id = 1;
    Thread first = createWith(claim, job);
    job.id = 2;
    Thread second = createWith(claim, job);

    let a = job.outcomes.receive();
    let b = job.outcomes.receive();
    assert(a.isReady() && b.isReady() && a.value != b.value);
    wait(first);
    wait(second);
    assert(job.state.get() == 1 || job.state.get() == 2);
    job.outcomes.close();
    println("one claimant won");
}
```

```text
one claimant won
```

## 21.4 超时不等于取消

waitFor(task, millis) 在非负毫秒上限内等待，完成返回 true，超时返回 false。超时后句柄仍需管理，可以再等待，也可以发出协作取消请求。tryWait(task) 相当于零等待时间的尝试。

requestStop 发出取消请求，任务要通过 stopRequested 或可取消等待来响应。它不会在任意一条赋值中间强行杀死线程。否则资源可能只更新一半，清理也无法按语言规则完成。

需要把任务失败作为数据查看时，waitResult 或 waitResultFor 返回状态、错误与调用栈。不要把没有异常输出理解为已经完成，也不要把“等待超时”记录成“任务失败”。ThreadGroup 可以集中承担多项任务的等待与取消责任；退出作用域前仍要理解哪些任务可能在等输入。

### 多次等待共用一个单调截止时间

如果连续两次等待都传入 `250` 毫秒，最慢可能分别等满这段时间。要让两次等待共用一份预算，先用 `Duration::fromMillis(250)` 表示时长，再用 `Instant::now().plus(budget)` 得到截止时刻。每次调用前用 `deadline.remaining().toMillisCeil()` 重新计算毫秒数。`Instant` 取自单调时钟，用于耗时和截止时间。它的读数起点由平台决定，日期时间应使用 `std::date_time`。

`Duration::fromNanos` 和 `Duration::fromMillis` 接收非负整数。毫秒转纳秒超出 `int64` 范围会触发断言。`Instant.plus` 在超出可表示的时刻时饱和到最大值。`end.durationSince(start)` 给出两者的非负间隔，反向区间返回零。`start.elapsed()` 以当前时刻为终点，`deadline.remaining()` 以当前时刻为起点，截止时间已到时返回零。

毫秒接口只能接收整数，`toMillisCeil()` 把不足一毫秒的正余量取整为一毫秒，避免把它提前变成零等待。这个转换最多增加不到一毫秒的取整误差。零毫秒表示立即尝试，如果业务要求到期后停止领取新结果，应先检查剩余时长是否为零。下面预先放好两条消息，让示例的输出不依赖线程调度。两次接收仍分别从同一个截止时刻计算各自的等待上限。

<!-- verify-book -->
```chali
import std::clock;
import std::concurrency;

void main() {
    let replies = Channel<int64>::create(2);
    assert(replies.send(10) == READY);
    assert(replies.send(20) == READY);
    replies.close();

    let start = Instant::now();
    let budget = Duration::fromMillis(250);
    let deadline = start.plus(budget);

    let first = replies.receiveFor(deadline.remaining().toMillisCeil());
    let second = replies.receiveFor(deadline.remaining().toMillisCeil());
    assert(first.isReady() && second.isReady());
    assert(start.remaining().toNanos() == 0);
    assert(Duration::fromNanos(1).toMillisCeil() == 1);
    println("sum={}", first.value + second.value);
}
```

```text
sum=30
```

## 21.5 网络等待与线程的选择

HTTP 文件服务器的套接字由创建它的上下文拥有，不能直接把每个套接字交给 createWith。第 28 章采用一个线程管理多个非阻塞连接：本轮没有数据就先处理下一条连接，有数据时只推进一小步。

这种并发处理避免一位慢客户端挡住其他连接，但不会让 CPU 密集计算自动在多个核心上并行。选择线程、消息还是事件循环，要从数据归属和等待位置出发。

### 用等待保证输出顺序

任务结束后主线程才输出最后一行。

<!-- verify-book -->
```chali
import std::thread;

void task() {
    println("finished");
}
void main() {
    Thread worker = create(task);
    wait(worker);
    println("joined");
}
```

```text
finished
joined
```
