学习一门语言，先建立可以反复操作的最小过程：写一个源文件，检查它，运行它，再解释屏幕上的结果。本章的问候程序只有一个输出调用，便于把工具问题与程序逻辑分开。后续再加入输入、数据和资源，也沿用这条验证过程。

阅读时请同时留意三种材料：源码告诉程序做什么，终端命令告诉编译器怎样处理文件，输出区记录运行结果。它们不能混写进同一文件。完成本章后，应能说明 main 在哪里、哪条命令执行了它，以及一次成功检查究竟证明了什么。

## 1.1 准备编译器与工具链

安装和平台要求见[安装说明](../39-installation-packages.md)。命令中的 `chali` 表示已加入 PATH 的编译器。Windows 源码构建产物使用类似 `chali-1.0.11-llvm-external-windows-x64.exe` 的名称，运行时换成实际路径；Linux 当前目录中的程序写作 `./chali`。

外置 LLVM 变体需要可用的 LLVM 工具链，内置变体携带相应编译组件。变体和目标支持范围分别核对；能启动编译器并不代表它能导出任意目标。

## 1.2 源文件与入口

先创建一个名为 `hello.chl` 的文本文件。文件扩展名帮助工具识别源码，但决定程序做什么的仍是文件内容。将下面的完整例程保存进去，暂时不用添加输入、变量或额外函数，这样第一次运行只需要关注一行输出。

程序会从 `main` 开始执行。可以把它看作本例的起点：进入花括号，执行里面的调用，再离开函数。先观察这个过程，随后再区分返回类型、函数名、字符串和分号分别承担的作用。

<!-- verify-book -->
```chali
void main()
{
    println("Hello, ChaLi!");
}
```

```text
Hello, ChaLi!
```

### 代码详解

从 `void main()` 读起：`void` 表示函数不返回业务值，`main` 是程序启动后进入的函数名，圆括号内没有形参。花括号内只有一个调用，因此运行时会执行一次 `println`，然后函数结束。

`"Hello, ChaLi!"` 是传给输出函数的字符串，双引号用来标记字符串边界，不会打印出来。`println` 在文本后补上换行，所以输出区只有一行。分号结束这条调用语句；花括号负责划定函数体，二者作用不同。这个例子没有输入，也没有分支，输出可以直接由唯一的调用确定。


## 1.3 检查与运行

在源文件所在目录执行：

```sh
chali check hello.chl
chali run hello.chl
```

### 代码详解

这两行是依次执行的终端命令，不是写进 hello.chl 的程序语句。第一行把该文件交给 `check`，检查通过时不会产生示例中的问候输出；第二行把同一文件交给 `run`，编译成功后才执行 main 并打印文本。

命令中的文件名相对于当前终端目录查找。若提示文件不存在，先核对保存位置与工作目录；若提示找不到 chali，则核对编译器路径。只有第二行实际运行了用户代码，不能用第一行成功代替输出验收。


check 执行前端检查，不运行用户程序。run 在检查通过后使用 checked AOT 编译并运行本机原生代码。它不是解释器：程序中的输入、文件操作和副作用发生在运行阶段。检查失败时，先处理首条诊断，再重新检查；后续消息可能由同一问题引起。

## 1.4 源码经过哪些阶段

前端解析声明和表达式，检查类型、借用、资源与控制流。正常 run／aot 路径从已检查 AST 生成 LLVM IR，由 LLVM 优化、生成机器码并完成链接。LLVM IR 与 ChaLi 四元式是不同表示；日常编写程序不需要手工修改它们。

aot 用于生成交付产物，第 24 章介绍输出、目标平台及依赖。程序版本以仓库 VERSION 为准，本书按当前已实现行为说明，不把计划特性作为语法。

## 1.5 阅读与定位问题

完整例程从 main 开始执行，声明可以写在它之前。交互程序另列测试输入；错误示例说明预期被拒绝的原因，不应拼入正常程序。小结和习题关注本章引入的概念，详细语法可查[语言参考](../04-language-reference.md)。

### 小结

从这一章起，每个完整例程都可以按“入口—调用—结果”阅读。先找到 main，再顺着执行顺序进入函数，最后与输出对照。出现错误时先定位检查、编译链接还是运行阶段，再使用对应信息处理，不要同时修改源码和工具配置后只看是否碰巧成功。

第 2 章会让程序停下来等待输入。那时结果不再只由源码决定，还取决于输入顺序，因此需要把测试输入也记录下来。

## 1.6 习题

1. 运行 hello.chl，核对换行。
2. 分别执行 check 和 run，哪个会输出文本？
3. 把语句末尾分号删去，记录首条诊断。
4. 区分编译器依赖与应用依赖。

### 参考解答与验收要点

1. 输出一行 Hello, ChaLi!。
2. run 执行程序；check 不执行输出。
3. 恢复分号后重新检查，不依赖诊断文字的固定行号。
4. LLVM 工具用于编译；应用所用动态库按交付约定准备。

## 1.7 番外：皇帝的新程序

改写自安徒生《皇帝的新装》。

许多年以前，有一位皇帝，为了运行得漂亮，不惜把所有的钱都花在买新程序上。他既不关心输入，也不关心输出，除非是为了炫耀他的新基准。他每一天钟头都要换一套编译选项。人们提到他，总是说：“皇上在优化器里。”

有一天来了两个骗子，自称能编出人类所能想象的最快程序。这程序还有一种奇怪的特性：凡是不称职或愚蠢得不可救药的人，都看不见它的输出。

“这正是我理想中的程序！”皇帝想，“有了它，我就能知道群臣里谁不懂技术。”于是付了许多预算，叫他们立刻开工。骗子架起两台显示器，整日敲空格；最好的服务器和显卡，却都装进了自己的口袋。

老大臣奉命去看，睁大眼睛，只见 `void main() {}`。他不敢说自己什么也没看见，便连连点头：“多么优美的输出！多么鲜艳的性能！”骗子请他描述结果，他说：“非常符合预期。”因为预期也没有写。

游行那天，皇帝举着空屏幕，内臣托着并不存在的进度条。百姓齐声称赞：“运行得真快！连日志也没有！”谁也不愿显得自己不称职。

“可是它什么也没做呀！”一个孩子终于叫了出来。

皇帝有点发抖，因为他觉得孩子说的似乎是对的。他心里却想：“这发布会必须坚持到底。”于是更加骄傲地举着屏幕，内臣们继续托着那根根本不存在的进度条。

### 技术对照

通过语法和类型检查，只能证明对应静态检查通过。程序是否产生预期输出、是否访问了外部资源，需要运行验证；外部输入变化也可能使后续运行失败。
