# 第 17 章 接口与具体类型匹配

<!-- LANGUAGE NAVIGATION -->
[English](en/17-interfaces.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

多个类型可以有不同字段，却提供相同操作。接口把调用方需要的行为集中起来，使处理函数不必为每种具体布局重写。图形和错误信息都适合说明这种关系。

本章先通过 Shape 引用调用各自实现，再在确有处理差异时识别 Error 中的具体类型。直接分派与具体类型匹配各有用途：前者共享行为，后者表达针对某种实现的专门处理。

## 17.1 先实现一份共同约定

<!-- verify-book -->
```chali
interface Shape
{
    int64 area();
    String describe();
};

struct Circle: Shape
{
    int64 r;

    int64 area()
    {
        return 3 * self.r * self.r;
    }
    String describe()
    {
        return "圆";
    }
};

void main()
{
    Circle c;
    c.r = 2;
    println("{}，面积 {}", c.describe(), c.area());
}
```

```text
圆，面积 12
```

Shape 声明 area、describe，规定调用者能够要求的两项行为。Circle 提供字段 r 和这两个方法；这里用 3*r*r 作教学用近似面积，未计算真实圆周率。main 先设半径 2，再调用两个方法，得到名称与 12。下一节把具体值放进接口变量，观察调用者怎样只依赖共同约定。

## 17.2 以行为组织调用

假设需要为不同图形生成说明。若调用者分别读取 r 或 side，就必须知道每一种布局；增加图形时也要修改调用者。Shape 让它只要求面积与名称这两项行为，具体字段留给实现决定。

report 因而可以接收接口引用，按统一方式调用方法。Circle 与 Square 的实现不同，传递关系却相同。这里先借用现有对象来观察分派，同时保留具体模型原本的值、资源和生命周期规则。

<!-- verify-book -->
```chali
interface Shape
{
    int64 area();
    String describe();
};

struct Circle: Shape
{
    int64 r;
    int64 area()
    {
        return 3 * r * r;
    }
    String describe()
    {
        return "圆";
    }
};

struct Square: Shape
{
    int64 side;
    int64 area()
    {
        return side * side;
    }
    String describe()
    {
        return "正方形";
    }
};

String report(Shape const& shape)
{
    return shape.describe() + "：" + format("{}", shape.area());
}

void main()
{
    Circle c;
    c.r = 2;
    Square s;
    s.side = 3;
    Shape const& shape1 = &c;
    Shape const& shape2 = &s;
    println("{}", report(shape1));
    println("{}", report(shape2));
}
```

```text
圆：12
正方形：9
```

Shape 只声明 area 与 describe 两种行为，不规定 r 或 side 字段。Circle 和 Square 各自实现它们，report 因而只需要 Shape const&，不用分支判断传入的是哪一种图形，也不复制或取得原对象的所有权。

main 把两个仍存活的对象分别借用为接口引用。圆的计算在示例中用整数 3 近似系数，半径 2 得到 12；正方形边长 3 得到 9。report 调用各自实现，把名称、冒号和面积字符串拼在一起。该例展示接口分派，不是高精度几何算法；接口引用也不能活得比 c、s 更久。


## 17.3 识别接口中的具体错误

IoError 实现 Error。match 可以在接口值中识别它，并把具体值绑定为 e；_ 接收其余实现，也可以写 _(other) 以命名回退值。开放接口一般需要回退分支，因为已列出的实现不构成对未来实现的穷尽。

<!-- verify-book -->
```chali
import std::io;
void describe(Error error)
{
    match (error)
    {
        std::io::IoError(e) => { println("io: {}", e.toString()); }
        _ => { println("other: {}", error.toString()); }
    }
}
void main()
{
    describe(std::io::IoError::Closed);
    describe(MessageError::from("invalid score"));
}
```

```text
io: 文件已关闭
other: invalid score
```

describe 的静态形参类型是 Error，但它保存的具体错误可以不同。第一次传入 IoError::Closed，类型模式识别出 std::io::IoError，并把具体值绑定为 e，因此打印带 io 前缀的关闭错误。

第二次传入 MessageError，没有命中 IoError 模式，进入 `_` 回退，使用 Error 接口的 toString 输出 invalid score。回退保留对其他实现的处理能力；如果所有分支只是调用相同接口方法，则通常不必先识别具体类型。这里加不同前缀，正是为了让两条处理路径可观察。


## 17.4 泛型接口与继承

接口可以带类型参数，也可以继承其他接口。泛型实参明确行为中使用的数据类型；继承表达所要求能力的包含关系。它不等于自动继承一个类的字段布局，也不能用强制转换伪造未实现的行为。泛型约束的完整示例见下一章。

## 17.5 何时匹配，何时调用

每个实现都能给出相同行为时直接调用接口方法。只有处理方式依赖具体错误、恢复策略或载荷字段时才细分类型。不要为了调用同一个 toString，在每个已知实现上重复写分支。Result 中接口载荷的匹配和传播在第 14 章给出。

### 小结

接口承诺可调用的方法，不承诺某一实现的字段布局。引用接口值时来源仍需存活，按值接口载荷也保留具体类型的值与资源语义。只有需要具体恢复策略或额外数据时再做类型细分。

下一章把“要求某种行为”进一步用于泛型约束，并用关联类型连接输入实现与输出类型。第 14 章再把接口错误放进 Result 的成功／失败结构。

## 17.6 在枚举载荷中细分错误

<!-- verify-book -->
```chali
import std::io;
Result<String, Error> readDemo()
{
    return Result<String, Error>::Err(std::io::IoError::ReadFailed("demo"));
}
void main()
{
    let result = readDemo();
    match (result)
    {
        Ok(text) => { println("{}", text); }
        Err::std::io::IoError(e) => { println("qualified: {}", e.toString()); }
        Err(_) => { println("other error"); }
    }
    match (result)
    {
        Ok(_) => { println("ok"); }
        std::io::IoError(e) => { println("short: {}", e.toString()); }
        Err(_) => { println("other error"); }
    }
}
```

```text
qualified: 读取失败：demo
short: 读取失败：demo
```

<!-- verify-book -->
```chali
import std::io;
enum Response
{
    Pending,
    Failed(int64 code, Error error)
};
void main()
{
    let response = Response::Failed(503, std::io::IoError::Closed);
    match (response)
    {
        Response::Pending => { println("pending"); }
        Response::Failed(code, std::io::IoError e) => { println("{}: {}", code, e.toString()); }
        Response::Failed(code, _ other) => { println("{}: {}", code, other.toString()); }
    }
    Result<Error, Error> result = Result<Error, Error>::Ok(std::io::IoError::Closed);
    match (result)
    {
        Ok(std::io::IoError e) => { println("ok: {}", e.toString()); }
        Ok(_) => { println("other success"); }
        Err(std::io::IoError e) => { println("err: {}", e.toString()); }
        Err(_) => { println("other failure"); }
    }
}
```

```text
503: 文件已关闭
ok: 文件已关闭
```

<!-- verify-book -->
```chali
import std::io;
Result<String, std::io::IoError> leaf()
{
    return Result<String, std::io::IoError>::Err(std::io::IoError::Closed);
}
Result<String, Error> readName()
{
    String name = leaf()?;
    return Result<String, Error>::Ok(name);
}
Option<std::io::IoError> optionalError()
{
    return Option<std::io::IoError>::Value(std::io::IoError::Closed);
}
Option<Error> widenedError()
{
    let error = optionalError()?;
    return Option<Error>::Value(error);
}
void main()
{
    match (readName())
    {
        Ok(name) => { println("{}", name); }
        Err(std::io::IoError e) => { println("result: {}", e.toString()); }
        Err(_) => { println("other error"); }
    }
    match (widenedError())
    {
        Value(std::io::IoError e) => { println("option: {}", e.toString()); }
        Value(_) => { println("other value"); }
        None => { println("absent"); }
    }
}
```

```text
result: 文件已关闭
option: 文件已关闭
```

第一例把 IoError 放进 Error 接口载荷，先用 Err::std::io::IoError(e) 明确写出标签与具体类型，再用无冲突时允许的简写。两次都保留 Err(_) 处理其他实现。

第二例增加一个普通 code 载荷，必须保留 Failed(code, IoError e) 的括号与各位置。后面的 Result<Error,Error> 特意把错误对象放在 Ok：载荷类型是 Error，并不能据此把成功状态判成 Err。

第三例的 leaf 返回具体 IoError，readName 的 ? 把失败提升到 Error 接口并提前返回；widenedError 则从 Option 的 Value 取得值，重新包装为接口载荷。先看外层标签，再看具体类型，这个顺序同时适用于两个或多个载荷。

## 17.8 番外：七十二变，一个接口

改写自《西游记》孙悟空变化斗法的情节。

却说二郎真君与大圣斗法，正斗到接口分派之处。大圣摇身一变，变作麻雀，飞在树梢。真君不问他祖籍，只问：“可会飞？”麻雀展开翅膀，便过了检查。

真君变作饿鹰，大圣变作大鹚老；真君变作海鹤，大圣变作鱼儿。八戒看得眼热，连忙定义一个“凡物都须划桨”的接口，拿给麻雀实现。麻雀说自己没长桨，八戒拍案：“没有桨，怎配叫过河？”

沙僧将接口改成“到对岸”，各物按本领实现。鸟飞，鱼游，筏子划。调用方总算不必先问对方究竟是飞禽还是外包。

大圣后来变作一座土地庙，把尾巴竖在后面当旗杆。八戒一见匾额上写着“可过河”，立刻给它盖了认证章。真君笑道：“旗杆竖在后面，已不合常理；更何况它根本没实现那个方法。”

大圣现了本相，说：“俺老孙七十二变，变的是实现，不是让调用者凭相貌猜合同。”八戒讪讪收回公章，又问默认实现能不能负责所有业务。真君将第三只眼一睁：“能负责你那条没写完的方法，负责不了你没想清楚的需求。”

### 技术对照

接口规定可调用的共同能力，实现类型决定具体行为。静态类型只公开接口声明的成员；默认实现和具体覆盖也要按实际分派规则验证。
