# 第 25 章 不安全代码：把责任留在小范围内

<!-- LANGUAGE NAVIGATION -->
[English](en/25-unsafe-code.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

前面的章节主要使用普通值、引用和标准容器。编译器替我们检查类型、借用与清理关系，运行时继续检查数组范围和分配寿命。实现分配器、容器或宿主适配时，有时还需要直接处理地址和尚未构造元素的空间。本章讲这些操作如何使用，以及程序员需要补上哪些证明。

本章之后再进入学生信息管理系统。业务代码通常继续使用安全接口；这里的知识主要用于实现接口背后的存储内核。完整 API 见[原始存储与 C ABI 指令](../44-unsafe-abi.md)。

本章的 `RawStorage`、`RawPtr`、`BarePtr`、`memcpy` 和 `memset` 都来自默认可用的 `std::lang`。示例省略 `std::lang::` 前缀，也不需要为这些名字额外写 `import`。

## 25.1 unsafe 允许什么

`unsafe { ... }` 建立不安全作用域。`unsafe` 函数把这个要求写进签名：调用者必须在不安全作用域内调用它，函数体也获得执行不安全操作的权限。

<!-- verify-book -->
```chali
unsafe int64 addOffset(int64 address, int64 bytes) {
    return address + bytes;
}

void main() {
    unsafe {
        println("{}", addOffset(100, 8));
    }
}
```

```text
108
```

把调用移到块外会在编译时被拒绝。闭包有自己的检查范围，不能因为在 `unsafe` 块里创建就自动获得权限。不安全函数值也不能悄悄变成普通函数值。

`unsafe` 不会把整个程序改成无检查模式。普通数组、算术和存活检查仍按原有规则执行。变化在于：编译器允许调用某些需要程序员保证额外条件的接口。

## 25.2 容量还不是元素

考虑一个容量为 100、长度为 3 的容器。它只需要拥有 3 个已构造的元素，其余 97 个位置只是备用空间。如果元素会打开文件或登记资源，扩容时把全部备用位置都默认构造出来，行为和成本都会改变。

`RawStorage<T>` 表示这样的独占空间。它记录容量、元素布局及逐槽初始化状态。`RawPtr<T>` 保存分配身份和下标，不拥有元素，也不延长分配寿命。

| 操作 | 调用前 | 调用后 |
| --- | --- | --- |
| `initAt` | 目标未初始化 | 目标拥有传入值 |
| `readAt` | 源已初始化 | 取得按值语义产生的副本，源仍有效 |
| `borrowAt` | 源已初始化 | 借出引用，所有权不变 |
| `takeAt` | 源已初始化 | 返回拥有值，源变为未初始化 |
| `dropAt` | 源已初始化 | 清理元素，保留容量 |
| `close` | 任意合法初始化状态 | 清理存活元素并释放整个分配 |

<!-- verify-book -->
```chali

void main() {
    RawStorage<String> slots = RawStorage<String>::allocate(4);
    unsafe {
        initAt<String>(slots.pointer(0), "hello");
        String result = takeAt<String>(slots.pointer(0));
        assert(!slots.isInitialized(0));
        println("{} / {}", result, slots.capacity());
    }
    slots.close();
}
```

```text
hello / 4
```

重复初始化、读取未初始化槽位、越界访问和释放后访问会报告错误。`pointer(capacity)` 可以形成尾后位置，不能解引用。泛型调用中显式写出 `<String>`，也能清楚说明当前操作针对哪一种元素。

## 25.3 复制、移动与清理分别负责什么

`readAt` 继续采用 ChaLi 的普通值语义。它不会因为身处 `unsafe` 就把 String 句柄直接当成独立副本。需要转移所有权时使用 `takeAt`，随后把返回值传给 `initAt`；需要丢弃元素时使用 `dropAt`。

`relocateNonOverlapping<T>(destination, source, count)` 先验证完整源、目标范围和槽位状态，再逐元素搬移。目标必须未初始化，范围不能重叠。成功后源槽位不再拥有元素。移动零个元素直接返回。

实现 `Closeable` 的资源不能同时声明 `Copy<T>` 或绕过 `#NonCopyable`。实验容器如果确实能产生独立副本，可以提供显式命名的复制方法，但仍要逐项建立新副本的所有权。

`RawStorage<T>::close()` 只清理已初始化元素。因此删除 List 尾部元素后可以保留容量，又不会把已经移出的元素再清理一次。借出的引用则必须在移出、清理或释放前停止使用；`borrowAt` 的不安全契约要求调用者保证这一点。

## 25.4 裸指针只留下地址

`BarePtr<T>` 保存一个 ChaLi 逻辑字节地址。它没有运行时类型标签、初始化位图或所有者字段。`T` 决定编译时怎样解释地址，以及指针算术使用多大的步长。

| 表示 | 保存的信息 | 主要用途 |
| --- | --- | --- |
| 普通引用 | 类型与语言借用关系 | 日常读取和修改值 |
| `RawPtr<T>` | 分配身份、槽位下标 | 受检初始化、读取、移出和清理 |
| `BarePtr<T>` | 字节地址 | 不检测类型的底层字节内核 |

`barePointer<T>(rawPointer)` 从原始分配取得裸地址，允许未初始化位置。`pointerFromAddress<T>(address)` 将数值地址解释为裸指针。`dereference<T>(pointer)` 把地址解释为 `T mut&`。这三种操作都要求 `unsafe`；它们不会替调用者证明布局、初始化和所有权正确。

这里的逻辑地址由 ChaLi 运行时管理，不能直接当作机器 C 指针交给宿主。需要与 C 交互时继续使用[第 21 章](21-与C互操作.md)的 ABI 适配。

`p.castTo<U>()` 保持地址不变，把 `BarePtr<T>` 改成 `BarePtr<U>` 视图，也要求 `unsafe`。例如先执行 `p.castTo<uint8>()`，就可以逐个字节解引用，并用 `+ 1` 前进一个字节。转换本身不检查目标类型、不分配也不复制；调用者必须保证目标布局、对齐、初始化状态和访问范围有效。

IEEE754 位模式转换也使用 `castTo` 及解引用。要区分物理槽和外部格式：ChaLi 的 `float32`、`float64` 都占八字节浮点槽，`float32` 的外部四字节 binary32 编码需要从槽内位模式还原，不能直接读取槽的前四字节。AOT 将对应转换降低为 LLVM 位转换和浮点宽度转换指令，指针视图包装在优化后消除；正负零、次正规数、无穷和 NaN 仍按编解码接口处理。

## 25.5 指针算术按元素走

对于 `BarePtr<int64>`，`p + 1` 前进一个 `int64`，即 8 字节。对于 `BarePtr<uint8>`，相同表达式前进 1 字节。

<!-- verify-book -->
```chali

void main() {
    RawStorage<int64> slots = RawStorage<int64>::allocate(3);
    unsafe {
        BarePtr<int64> p = barePointer<int64>(slots.pointer(0));
        BarePtr<int64> q = p + 2;
        assert(q.address - p.address == 16);
        assert((2 + p).address == q.address);
        q = q - 1;
        println("{} / {}", q - p, q.address - p.address);
    }
    slots.close();
}
```

```text
1 / 8
```

支持 `p + n`、`n + p`、`p - n` 和同类型的 `p - q`。最后一种返回元素距离，字节距离必须恰好是完整元素的倍数。调用者应只对同一分配计算距离；这个条件不能从两个裸地址本身证明。

地址算术不会读取内存，可以先算出尾后地址。但一个可计算的地址不一定可解引用。负偏移、乘法、加减和除法仍遵循普通整数运算规则。

## 25.6 memcpy 与 memset 按字节工作

`memcpy<T,U>(destination, source, bytes)` 复制字节。源与目标可以使用不同的静态元素类型，底层不检查它们是否一致。`memset<T>(destination, value, bytes)` 把指定字节重复写入目标范围。

虽然调用形式像函数，编译器将它们直接降低为专门的四元式；VM 执行字节指令，LLVM AOT 使用 `memcpy`／`memset` intrinsic。必要的地址和完整范围检查仍在写入前执行。

长度都是**字节数**。对 `BarePtr<int64>` 填充 8 字节，只覆盖一个元素，而不是 8 个元素。`memset(p, 1, 8)` 写入的是 8 个 `0x01` 字节，并不等于向一个 `int64` 写入整数 1。

<!-- verify-book -->
```chali

void main() {
    RawStorage<int64> source = RawStorage<int64>::allocate(1);
    RawStorage<uint8> target = RawStorage<uint8>::allocate(8);
    unsafe {
        BarePtr<int64> from = barePointer<int64>(source.pointer(0));
        BarePtr<uint8> to = barePointer<uint8>(target.pointer(0));
        memset<int64>(from, (uint8)42, 8);
        memcpy<uint8,int64>(to, from, 8);
        uint8 mut& first = dereference<uint8>(to);
        uint8 mut& last = dereference<uint8>(to + 7);
        println("{} / {}", (int64)*first, (int64)*last);
        assert(!source.isInitialized(0));
    }
    source.close();
    target.close();
}
```

```text
42 / 42
```

非零范围必须位于有效分配内。复制在完整源和目标范围都验证成功后才写入；重叠范围会被拒绝。零长度允许空指针。`memcpy` 采用非重叠复制约定，容器内部移动重叠区域时需要另行设计方向和所有权转移。

## 25.7 字节写入不等于构造资源值

上个程序写入了原始字节，但 `source.isInitialized(0)` 仍为 `false`。这是明确的接口约定：裸字节操作不读写逐槽初始化位图，也不调用复制、移动和清理钩子。

对字节缓冲区，这样可以一次复制整段内容。对 String 或文件资源，只复制句柄字节不会产生第二份所有权。把两份相同句柄分别交给清理逻辑，就可能重复释放。向一个存活资源写入全零，也不会替原资源执行清理。

因此，字节操作负责字节，资源操作负责所有权。需要把一个资源从容器移到另一个容器时，继续使用 `takeAt`、`initAt` 或满足条件的搬移接口。

裸指针还不携带分配代次。释放后不能继续使用旧地址，也不能因为后来某个地址再次可访问，就认定它仍然表示原对象。

## 25.8 把不安全操作封装在安全接口内

实现一个字节缓冲区时，可以让公开的 `pushByte`、`getByte` 和 `reserve` 检查长度、容量与溢出，把裸指针操作收进方法内部的小块 `unsafe`。调用者只接触缓冲区，不直接维护地址与容量之间的关系。

扩容按以下顺序执行：先申请新容量，再复制存活字节，成功后释放旧分配，最后更新指针和容量。不要先释放旧空间再读取它，也不要在复制失败前把新指针公布给调用者。资源元素还要在这个顺序中正确转移初始化状态。

完整实验在 [`bootstrap_string.chl`](../../benchmarks/perf/bootstrap_string.chl)。它实现独占字节存储、扩容、追加、读取、查找和显式独立复制；中文与 emoji 按 UTF-8 字节保存。它没有实现标准 String 的全部 Unicode 方法，也不会因为按字节存储就自动知道一个下标是不是码点边界。

实现同类接口时，先写出不变量，例如 `0 <= length <= capacity`、`data` 指向当前拥有的分配、每次解引用都位于有效字节范围。每个不安全块旁边都应能解释它为什么满足这些条件。

## 25.9 用正确性与测量判断实现

原始存储的正确性测试应覆盖空容量、边界、重复初始化、移出后读取、增长、删除保留容量、释放后访问以及资源只清理一次。裸字节操作还要验证零长度、跨类型复制、重叠拒绝、完整范围检查和填充值的字节含义。

性能测试要把编译与执行分开，用相同输入和可核对的输出比较。构造、逐字节追加、读取、查找、复制及原生 String 转入自举存储应分别记录。批量复制可能减少逐字节调用，但不能据此推断全部操作都会更快；查找算法、分配方式和剩余检查同样影响结果。

[原生与自举 String 报告](../../benchmarks/results/string-1.0.7/README.md)保留实际源码和编译器摘要。较早的逐槽受检版保存在 `bootstrap_string_checked.chl`，不能把它的测量改标为新的裸指针版。VM 与 AOT 也要分别记录。

## 25.10 小结

| 工具 | 程序员承担的主要责任 |
| --- | --- |
| `unsafe` 作用域／函数 | 解释接口额外条件为何成立 |
| `RawStorage<T>` | 维护元素初始化与所有权转移 |
| `BarePtr<T>` | 维护地址、布局、对齐、寿命和有效访问范围 |
| 指针算术 | 区分元素步长与字节距离，控制有效位置 |
| `memcpy`／`memset` | 使用正确字节数，避免重叠和错误资源所有权 |
| 安全封装 | 将长度、容量及清理约束收在接口内部 |

日常业务优先使用标准容器和普通引用。需要实现存储内核时，再把这些工具放进范围明确、能够单独验证的小接口里。接下来进入[第 26 章的学生信息管理系统](26-学生信息管理系统.md)。

## 25.11 习题

1. 把 25.1 的调用移到 `unsafe` 块外，再尝试在块里创建一个调用该函数的普通闭包，分别观察诊断。
2. 在 25.2 中先 `takeAt`，再对同一槽位调用 `readAt`。为什么不能把剩余字节当成有效 String？
3. 将 25.5 的元素类型改为 `uint8`，说明两处地址差和元素距离应如何改变。
4. 把 25.6 的填充值改为 1，再将源作为 `int64` 解释。为什么结果不是整数 1？
5. 对同一分配的前 8 字节和后移 1 字节的位置调用 `memcpy`，确认重叠被拒绝。再尝试零长度空指针复制。
6. 挑战：给实验字节缓冲区补充一次自身追加，并验证扩容后仍能正确读取原内容、复制独立性和最终清理。

### 参考解答与验收要点

1. 普通作用域调用不安全函数会被拒绝。闭包重新建立自己的函数权限范围，创建位置的不安全权限不会自动传入。
2. 移出已经转移所有权并把源标记为未初始化。旧字节不再表示源位置拥有的值；再次读取会被槽位状态检查拒绝。
3. `uint8` 每次前进 1 字节，`p + 2` 的字节距离为 2。减去一个元素后，元素距离与字节距离都为 1。
4. 每一个字节都被写成 `0x01`。一个 8 字节整数的完整位模式与仅最低有效字节为 1 的整数不同。
5. 非零重叠范围违反接口约定。零长度不访问内存，允许两个空指针，不会复制或填充任何字节。
6. 扩容前记录原长度，复制时使用更新后的有效地址，目标位于原内容之后；新旧存储的交接只能发生在复制成功之后。分别验证不扩容和需要扩容的情况。

## 25.12 番外：油杓与葫芦

改写自欧阳修《卖油翁》。

陈尧咨见老翁酌油，问道：“既然手熟，何必还要铜钱？”翁曰：“钱孔使我看清边界，手熟使我守住边界，二者并不相妨。”

有门客闻言，将铜钱收进袖里，又在葫芦上贴了“不安全”三字，自谓已尽得要领。油未入瓶，先湿了衣袖。公问其故，门客答：“既已声明不安全，自然可以不问油流向哪里。”

翁取杓而止之：“你可以亲手持杓，却不能把别人的葫芦当作自己的。倒进去的是油，不是瓶子的主人；抄下来的是瓶号，也不是第二只瓶子。”

于是门客把取油、持杓、换瓶各写一条规矩，替客人留下一个稳妥的把手。客人只须接过葫芦，如何守住钱孔，仍由持杓的人负责。公笑曰：“这回写在纸上的，终于不是免罪的告示。”

### 技术对照

`unsafe` 表明实现者承担额外证明义务。裸地址和按位复制不会产生资源所有权，范围检查与清理协议仍各有职责。把底层操作封装成接口，是让调用者使用已经维护好的不变量；性能则要通过实际负载检验，不能由一个关键字推断。
