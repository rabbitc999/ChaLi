\chapter{闭包与高阶函数}
\label{ch:15}

排序的比较方式、筛选的条件和完成后的处理都可能变化，而遍历框架可以保持不变。函数值把这部分行为作为数据传递；闭包还保存行为所需的环境，让调用不只依赖显式参数。

本章先拆读嵌套函数类型，再用组合函数和捕获示例跟踪调用顺序。随后讨论返回闭包、共享来源、具名函数和递归。每个例程都同时回答“调用哪个函数”和“它读取哪份环境”。

\section{把函数作为参数}

先把 \texttt{int64 fn(\allowbreak{}int64)\allowbreak{}} 当成一种普通类型：它描述一项接收整数并返回整数的行为。接收这个类型的函数，不负责规定行为怎样实现，只负责在合适位置调用它。这样便能把固定流程与可变化的步骤拆开。

本节的第一个例程把这种关系多嵌套几层。阅读时先只看 level1 与 level2，再逐层加入外面的函数类型；后面的 compose 则把同样思想用于更常见的函数组合。嵌套签名很长时，执行顺序仍可以用一串普通调用表示。

\par
\medskip
\begin{lstlisting}[style=chali]
int64 level1(int64 value)
{
    return value + 1;
}

int64 level2(int64 fn(int64) callback)
{
    return callback(10);
}

int64 level3(int64 fn(int64 fn(int64)) callback)
{
    return callback(level1);
}

int64 level4(int64 fn(int64 fn(int64 fn(int64))) callback)
{
    return callback(level2);
}

int64 level5(int64 fn(int64 fn(int64 fn(int64 fn(int64)))) callback)
{
    return callback(level3);
}

int64 hello(
    int64 fn(int64 fn(int64 fn(int64 fn(int64 fn(int64))))) pipeline,
    int64 fn(int64) finish)
{
    return finish(pipeline(level4));
}

void main()
{
    int64 factor = 2;
    int64 finish(int64 value)
    {
        return value * factor;
    }
    println("{}", hello(level5, finish));
}
\end{lstlisting}
\par
\medskip

\par
\medskip
\begin{lstlisting}[style=out]
22
\end{lstlisting}
\par
\medskip

\subsection*{代码详解}

先把最内层 \texttt{int64 fn(\allowbreak{}int64)\allowbreak{}} 读成“接收整数、返回整数的函数”。每向外多包一层 fn，参数就变成前一层的函数值，而各层最终仍返回 int64。level2 负责把数字 10 交给回调，其他 level 只负责把下一层所需的函数传下去，声明函数本身并不会立刻执行它。

从 main 跟踪实际调用：hello 收到 level5 和 finish，先计算 level5(level4)，随后依次进入 level4(level3)、level3(level2)、level2(level1)，最后执行 level1(10) 得到 11。结果沿调用链返回，再交给 finish。finish 捕获 main 中的 factor=2，于是输出 22。复杂签名的关键是分清“传函数”与“调用函数”，不是把 level 编号当成递归次数。

\par
\medskip
\begin{lstlisting}[style=chali]
T fn(T) compose<T>(T fn(T) a, T fn(T) b)
{
    return fn copy(T x)
    {
        a(b(x))
    };
}

int64 increment(int64 value)
{
    return value + 1;
}

int64 twice(int64 value)
{
    return value * 2;
}

void main()
{
    let combined = compose(increment, twice);
    println("{}", combined(6));
}
\end{lstlisting}
\par
\medskip

\par
\medskip
\begin{lstlisting}[style=out]
13
\end{lstlisting}
\par
\medskip

\subsection*{代码详解}

compose 的返回类型 \texttt{T fn(\allowbreak{}T)\allowbreak{}} 是一个函数值，而不是当场算出的 T。返回闭包以 copy 捕获 a、b，使 compose 调用结束后，返回值仍持有后续调用所需的环境。闭包体的末尾表达式表示先调用 b，再把结果交给 a。

main 把 increment 作为 a、twice 作为 b，创建 combined 时还没有对 6 做运算。执行 combined(6) 才先得到 twice(6)=12，再得到 increment(12)=13。调换两个实参会改变组合顺序，不能把 \texttt{a(\allowbreak{}b(\allowbreak{}x)\allowbreak{})\allowbreak{}} 误读为先 a 后 b。泛型 T 要在两个函数的输入、输出之间一致。

\section{捕获与独立副本}

只读捕获、可变捕获和 copy 捕获表达不同访问关系。需要独立快照时显式选择复制；需要改变共享状态时核对可变访问。闭包副本中的环境是否独立，由捕获与复制规则决定，不能从调用语法猜测。

\par
\medskip
\begin{lstlisting}[style=chali]
void main()
{
    int64 n = 1;
    let f = fn mut(x) { n = x + n };
    let g = fn copy(x) { x * n };
    println("{} {} {}", f(1), g(1), n);
}
\end{lstlisting}
\par
\medskip

\par
\medskip
\begin{lstlisting}[style=out]
2 1 2
\end{lstlisting}
\par
\medskip

\subsection*{代码详解}

创建 f 时，mut 捕获让它可以写回外部 n；创建 g 时，copy 捕获保存 n 当时为 1 的独立值。两份环境在实际调用之前就已确定，不是每调用一次 g 都重新从外部取一份快照。

输出实参中先调用 f(1)，它将外部 n 改为 2，并产生本例所示的结果 2；g(1) 仍用快照 1 相乘，得到 1；最后读取外部 n 得到 2。于是打印 \texttt{2 1 2}。这个对比解释捕获关系，而不是说所有闭包副本都共享一个 n。

\par
\medskip
\begin{lstlisting}[style=chali]
void main()
{
    String a = "1";
    String fn() b = fn copy()
    {
        a
    };
    println("{} {}", a, b());
}
\end{lstlisting}
\par
\medskip

\par
\medskip
\begin{lstlisting}[style=out]
1 1
\end{lstlisting}
\par
\medskip

\subsection*{代码详解}

\texttt{String fn(\allowbreak{})\allowbreak{} b} 声明一个无参数、返回 String 的函数值变量。右侧的 fn copy() 保存 a 的值，闭包体最后的 a 就是每次调用产生的结果。copy 捕获没有把外部 a 移走，因此 main 仍能正常打印它。

\texttt{b(\allowbreak{})\allowbreak{}} 才是调用；单独的 b 是函数值。输出先读取外部字符串，再调用闭包取得其保存的字符串，两项都为 1。相同文本不代表它们可以通过任意修改互相影响；捕获方式才决定数据关系。

\section{返回闭包与环境存活}

返回一个闭包时，被保留的环境必须在后续调用期间有效。局部借用不能因包装成函数值而延长生命周期。下面的工厂示例区分不同闭包实例与它们各自的计数状态。

\par
\medskip
\begin{lstlisting}[style=chali]
int64 fn() makeNamedCounter()
{
    int64 current = 0;
    int64 next() move
    {
        current++;
        return current;
    }
    return next;
}

void main()
{
    int64 base = 10;
    int64 read()
    {
        return base;
    }
    int64 increment() mut
    {
        base++;
        return base;
    }
    int64 isolated() copy
    {
        base += 100;
        return base;
    }
    int64 initial = read();
    int64 changed = increment();
    int64 snapshot = isolated();
    println("{} {} {} {}", initial, changed, snapshot, base);

    let counter = makeNamedCounter();
    int64 first = counter();
    int64 second = counter();
    println("{} {}", first, second);

    int64 callback(int64 value);
    callback = int64 fn(int64 value)
    {
        return value + 1;
    };
    println("{}", callback(5));
}
\end{lstlisting}
\par
\medskip

\par
\medskip
\begin{lstlisting}[style=out]
10 11 110 11
1 2
6
\end{lstlisting}
\par
\medskip

\subsection*{代码详解}

先看 main 的三个局部函数：read 读取外部 base，increment 以 mut 捕获把它加一，isolated 以 copy 保存创建时的 10。依次调用后，initial=10、changed=11，而 isolated 把自己的副本加到 110；外部 base 仍为 11，所以第一行是 \texttt{10 11 110 11}。

makeNamedCounter 以 move 把 current 交给返回的 next 环境，工厂退出后计数状态仍由闭包拥有。对同一个 counter 连续调用，current 由 0 变 1、再变 2，不会每次重新初始化。最后先声明 callback 的函数签名，再赋入一个加一闭包，callback(5) 得到 6。三个部分分别演示捕获关系、返回环境的存活，以及函数值变量的赋值。

\par
\medskip
\begin{lstlisting}[style=chali]
fn makeAdder(int64 mut& amount) -> (int64 fn(int64))
{
    return fn(int64 value)
    {
        value + amount
    };
}
void main()
{
    int64 one = 1;
    int64 ten = 10;
    let plus1 = makeAdder(&one);
    let plus10 = makeAdder(&ten);
    println("{} {}", plus1(5), plus10(5));
}
\end{lstlisting}
\par
\medskip

\par
\medskip
\begin{lstlisting}[style=out]
6 15
\end{lstlisting}
\par
\medskip

\subsection*{代码详解}

makeAdder 接收来自调用方的 amount 引用，并返回使用该来源的闭包。one 与 ten 是 main 中两个不同对象，因此 plus1 与 plus10 虽然类型相同，环境所关联的来源也不同。

对相同输入 5 调用，分别读取 1 与 10，得到 6 和 15。返回函数值不会把原对象的生命周期要求消除；本例让 one、ten 在所有调用期间保持存活。不能仿照此模式返回借用已经结束的工厂局部对象的闭包，也不能把这类带环境函数值直接当作 C 函数指针。

\section{递归与具名函数值}

递归需要一个可在函数体中引用的调用目标，并且需要终止条件。具名函数值也能携带环境；复制函数值后继续调用时，要检查哪些状态属于副本，哪些来自显式共享关系。

\par
\medskip
\begin{lstlisting}[style=chali]
void main()
{
    int64 fn(int64) fac;
    fac = fn(x)
    {
        if (x >= 1)
        {
            fac(x - 1) * x
        }
        else
        {
            1
        }
    };
    println("fac(3)={}", fac(3));
}
\end{lstlisting}
\par
\medskip

\par
\medskip
\begin{lstlisting}[style=out]
fac(3)=6
\end{lstlisting}
\par
\medskip

\subsection*{代码详解}

先声明 fac 的函数类型，再把闭包赋给它，使函数体中的 fac 指向这个可调用目标。参数 x 从 3 逐次减小，x>=1 时递归求 fac(x-1) 再乘 x；x=0 时进入 else，返回乘法单位值 1，形成终止条件。

展开计算是 fac(3)=fac(2)*3，fac(2)=fac(1)*2，fac(1)=fac(0)*1，最后得到 6。若没有 else 的终止路径，就会不断递归；也不能在 fac 尚未被赋入合法函数值时调用它。示例只演示小的非负输入，没有处理大数溢出与递归深度。

\par
\medskip
\begin{lstlisting}[style=chali]
void main()
{
    int64 shift = 100;
    fn addShift(int64 value) -> int64
    {
        return value + shift;
    }
    fn describe()
    {
        println("shift is {}", shift);
    }
    println("{}", addShift(4));
    describe();
}
\end{lstlisting}
\par
\medskip

\par
\medskip
\begin{lstlisting}[style=out]
104
shift is 100
\end{lstlisting}
\par
\medskip

\subsection*{代码详解}

addShift 用 fn 前缀和箭头后的 int64 指明返回类型，函数体读取所在 main 中的 shift；它仍是能携带环境的具名函数。describe 没有返回业务值，作用是输出同一个环境中的 shift。

main 先调用 addShift(4)，得到 104，再调用 describe 打印 shift is 100。前一次加法只是返回计算结果，没有修改 shift，因而第二行仍为 100。两种函数写法的差异要结合签名理解，不能把省略返回值误认为能返回任意类型。

\section{调用边界与成本}

闭包的环境创建、复制、清理和间接调用都有各自成本。是否能内联由已知目标、环境和优化器共同决定；语言不保证每个闭包都消除分配。同步宿主回调使用项目规定的函数值协议，不能把运行期函数值直接强转成机器函数指针。

\subsection*{小结}

函数类型描述参数和返回值，捕获方式描述环境关系，生命周期决定后续调用是否合法；签名相同不能代替后两项判断。copy 保存独立值，mut 允许相应写回，move 把需要的拥有状态交给环境。

把复杂调用拆成中间结果，有助于核对先后顺序与副作用。返回闭包前检查来源，跨宿主边界时使用受支持的协议，不把语言函数值直接转换为机器回调指针。下一章让这些调用明确表达缺失与失败。

\section{习题}

\begin{enumerate}

\item 把一个处理函数传给高阶函数。

\item 复制闭包后怎样检查状态独立性？

\item 为何不能返回指向已结束局部作用域的借用？

\item 闭包是否都能转换成 C 函数指针？

\end{enumerate}

\subsection*{参考解答与验收要点}

\begin{enumerate}

\item 核对参数和返回类型后比较执行结果。

\item 分别调用原值与副本，观察计数器或文本是否按捕获规则变化。

\item 被引用对象已失效；函数值包装不会延长其存活。

\item 不能，环境和调用协议不同；使用受支持的同步回调桥接。

\end{enumerate}

\section{番外：孔乙己与闭包}

改写自鲁迅《孔乙己》，正文采用本书读者提供的改编稿。人物对白中的判断不代替本章的语言规则。

鲁镇的码栈的格局，是和别处不同的：都是当街一个曲尺形的大柜台，柜里面预备着服务器，可以随时跑代码。做工的人，傍午傍晚散了工，每每花四文铜钱，开一个沙箱——这是二十多年前的事，现在每个沙箱要涨到十文——靠柜外站着，快快地编译了休息；倘肯多花一文，便可以买一碟调试用例，或者跑一段开心代码，做练手项目了；如果能出到十几文，那就可以买一个完整项目。但这些顾客，多是短衣帮，大抵没有这样阔绰。只有穿格子衫的，才踱进店面隔壁的房子里，要项目要算力，慢慢地坐写。

我从十二岁起，便在镇口的咸亨码栈里当伙计。掌柜说，样子太傻，怕侍候不了格子衫主顾，就在外面做点事罢。外面的短衣主顾，虽然容易说话，但唠唠叨叨缠夹不清的也很不少。他们往往要亲眼看着代码从沙箱里拉出，看过你的代码有没有水，又亲看将沙箱放到服务器上，然后放心。在这严重监督下，掺水也很为难。所以过了几天，掌柜又说我干不了这事。幸亏荐头的情面大，辞退不得，便改为专管跑代码的一种无聊职务了。

我从此便整天地站在柜台里，专管我的职务。虽然没有什么失职，但总觉得有些单调，有些无聊。掌柜是一副凶脸孔，主顾也没有好声气，教人活泼不得；只有孔乙己到店，才可以笑几声，所以至今还记得。

孔乙己是站着接单而穿格子衫的唯一的人。他身材很高大；青白脸色，皱纹间时常夹些伤痕；一部乱蓬蓬的花白胡子。穿的虽然是格子衫，可是又脏又破，似乎十多年没有补，也没有洗。他对人说话，总是满口捕获借用，教人半懂不懂的。因为他姓孔，别人便从描红纸上的“上大人孔乙己”这半懂不懂的话里，替他取下一个绰号，叫作孔乙己。

孔乙己一到店，所有写代码的人便都看着他笑。有的叫道：“孔乙己，你头顶又空出一块了！”

他不回答，只对柜里说：“开两个沙箱，跑一段开心代码。”说完，排出九文大钱。

他们又故意高声嚷道：“你一定又写返回闭包了！”

孔乙己睁大眼睛说：“你怎么这样凭空污人清白……”

“什么清白？我前天亲眼见你写了个返回闭包，被编译器报 CHL1204，吊着打。”

“那是借用没活够。我后来改成 \texttt{fn make\allowbreak{}Counter(\allowbreak{})\allowbreak{} -\allowbreak{}>\allowbreak{} fn(\allowbreak{}int64)\allowbreak{} -\allowbreak{}>\allowbreak{} int64}，交出去的是闭包，借的都在里头。”

“你那箭头还写在 lambda 上呢，\texttt{fn (\allowbreak{}int64 x)\allowbreak{} -\allowbreak{}>\allowbreak{} int64 \{ .\allowbreak{}.\allowbreak{}.\allowbreak{} \}}，0.12.0 就废了。”

孔乙己便涨红了脸，额上的青筋条条绽出，争辩道：“那是 lambda！……具名函数后置，能算一回事么？……借用不能算逃逸……闭包！……程序员的事，能算逃逸么？”

接着，便是一串难懂的话，什么“const\& 只读”，什么“mut\& 写回”，什么“返回类型后置”，引得众人都哄笑起来。店内外充满了快活的空气。

听人家背地里谈论，孔乙己原来也读过书，还钻研过语言设计，但终于没有当程序员，又不会营生。于是愈过愈穷，弄到将要断网了。幸而写得一手好代码，便替人家敲敲代码，接点外包，换一点托管费。

可惜他又有一样坏脾气，便是好闲懒做。坐不到几天，便连人和电脑键盘鼠标，一齐失踪。如是几次，叫他接外包的人也没有了。

孔乙己没有法，便免不了偶然做些偷窃的事。但他在我们店里，品行却比别人都好，就是从不拖欠。虽然间或没有现钱，暂时记在粉板上，但不出一月，定然还清，从粉板上拭去了孔乙己的名字。

孔乙己跑过半段代码，涨红的脸色渐渐复原。旁人便又问道：“孔乙己，你当真会闭包么？”

孔乙己看着问他的人，显出不屑置辩的神气。

他们便接着说道：“你怎的连半个 counter 也捞不到呢？”

孔乙己立刻显出颓唐不安模样，脸上笼上了一层灰色。嘴里说些话，这回全是“默认捕获是只读借用”之类，一句也听不懂了。

这时候，众人也都哄笑起来。店内外充满了快活的空气。

在这些时候，我可以附和着笑，掌柜是决不责备的。而且掌柜见了孔乙己，也每每这样问他，引人发笑。

孔乙己自己知道不能和他们谈天，便只好向孩子说话。

有一回，他对我说道：“你读过书么？”

我略略点一点头。

他说：“读过书……我便考你一考。闭包的捕获方式，有几种？”

我想，连沙箱都开不起的人，也配考我么？便回过脸去，不再理会。

孔乙己等了许久，很恳切地说道：“不能写罢？……我教给你，记着！这些方式应该记着。将来写回调的时候，要用。”

我暗想，我和写回调的还差得远呢。再说，我们掌柜也从不把闭包上账。我又好笑，又不耐烦，懒懒地答他：“谁要你教，不是四种么？”

孔乙己显出极高兴的样子，将两个指头的长指甲敲着柜台，点头说：“对呀对呀！……闭包有四种捕获，你知道么？”

我愈不耐烦了，努着嘴走远。

孔乙己刚用指甲在柜台上画 fn counter() -> int64，又添一句“不写箭头就是 void”，见我毫不热心，便又叹一口气，显出极惋惜的样子。

有几回，邻舍孩子听得笑声，也赶热闹，围住了孔乙己。他便给他们一人一段ChaLi代码。

孩子跑完示例，仍然不散，眼睛都望着屏幕。

孔乙己着了慌，伸开五指将屏幕罩住，弯腰下去说道：“不多了，我已经不多了。”

直起身又看一看屏幕，自己摇头说：“不多不多！多乎哉？不多也。”

于是这一群孩子都在笑声里走散了。

孔乙己是这样的使人快活，可是没有他，别人也便这么过。

有一天，大约是中秋前的两三天，掌柜正在慢慢结账，取下粉板，忽然说：“孔乙己长久没有来了。还欠十九个钱呢——那还是违约金零头。”

我才也觉得他的确长久没有来了。

一个写代码的人说道：“他怎么会来？……他写代码写垮了。”

掌柜说：“哦！”

“他总仍旧是接外包。这一回，是自己发昏，竟接了个写编译器的大项目。那家的活，是人接的么？”

“后来怎么样？”

“怎么样？先写文档，后来是改，改了大半夜，越改越写不出来。”

“那家的活，难在哪？”

“难在哪？闭包捕获要全过，借用检查要全过，循环引用检测要全过，还要零警告。少一样，都不算交付。”

“后来呢？”

“后来交不出货了。”

“交不出货怎样呢？”

“怎样？……合同上写着违约金，许是赔不起了。”

掌柜也不再问，仍然慢慢算他的账。

中秋过后，秋风一天凉比一天。看看将近初冬，我整天靠着火，也须穿上棉袄了。

一天的下半天，没有一个顾客，我正合了眼坐着。忽然间听得一个声音：“开一个沙箱。”

这声音虽然极低，却很耳熟。看时又全没有人。

站起来向外一望，孔乙己便在柜台下，对着门槛坐着。

他脸上黑而且瘦，已经不成样子；穿一件破夹袄，怀里抱着个旧键盘，手指还搭在键帽上；见了我，又说道：“开一个沙箱。”

掌柜也伸出头去，一面说：“孔乙己么？你还欠十九个钱呢——违约金零头还没清呢！”

孔乙己很颓唐地仰面答道：“这……下回还清罢。这一回是现钱，代码要新。”

掌柜仍然同平常一样，笑着对他说：“孔乙己，你又写循环引用了！”

但他这回却不十分分辩，单说了一句：“不要取笑！”

“取笑？要是不写，怎么连回收器都不拦你，跑出来个 counter 只涨不跌？”

孔乙己低声说道：“循环引用，对象里存闭包，闭包又捕获对象，环套环，回收不掉的……”

他的眼色，很像恳求掌柜，不要再提。

此时已经聚集了几个人，便和掌柜都笑了。

我开了沙箱，放到门槛上。

他从破衣袋里摸出四文大钱，放在我手里。见他满手是茧，指节上还有键帽印，原来，他便用这手敲了一路的代码。

不一会，他跑完代码，便又在旁人的说笑声中，抱着旧键盘，慢慢走去了。

自此以后，又长久没有看见孔乙己。到了年关，掌柜取下粉板说：“孔乙己还欠十九个钱呢——违约金零头。”

到第二年的端午，又说：“孔乙己还欠十九个钱呢——违约金零头。”

到中秋可是没有说，再到年关也没有看见他。

我到现在终于没有见——大约孔乙己的确死了。

\subsection*{技术对照}

返回闭包本身合法；问题是它是否携带活得不够久的借用。默认只读借用、mut 写回借用、copy 拥有副本和 move 转移拥有关系各有规则。循环持有与借用逃逸也不是同一个问题，应按实际所有权图和宿主资源协议分析，不能从人物对白推断存在通用追踪式回收器。
