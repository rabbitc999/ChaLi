\chapter{部署原生产物}
\label{ch:22}

从 1.0.8 起，ChaLi 使用 AOT 作为运行与交付路径。\texttt{run} 编译并执行 checked 原生产物，\texttt{aot} 默认导出 unchecked 原生产物。\texttt{.\allowbreak{}svmb} 及其导出命令已删除，不再作为部署格式。

\section{开发时运行}

\par
\medskip
\begin{lstlisting}[style=sh]
chali run app.chl
chali run app.chl --out build/app
\end{lstlisting}
\par
\medskip

运行所需的编译器与 LLVM 工具链必须可用；外置 LLVM 变体使用安装好的 clang，静态变体使用内置 LLVM。\texttt{run} 开启数组与指针检查，普通所有权、借用与资源规则继续生效。

\section{交付时导出}

\par
\medskip
\begin{lstlisting}[style=sh]
chali aot app.chl --out build/app
chali aot app.chl --checked --out build/app-checked
\end{lstlisting}
\par
\medskip

第一条命令采用 unchecked 导出默认值，第二条显式保留数组和指针检查。两种产物都保留实际内存访问与对象存活验证；unchecked 不允许绕过所有权或静态借用规则。

将生成的原生可执行文件交给同平台、同架构的用户。Windows 使用 \texttt{.\allowbreak{}exe}，Linux 使用无后缀可执行文件；应用声明的 C ABI 动态库及必要资源文件一并交付。目标机器运行产物不需要 ChaLi 编译器、VM 或 LLVM 动态库。

跨架构构建编译器不等于相应 AOT 目标已支持。实际目标和验证范围见\href{https://github.com/rabbitc999/ChaLi/blob/master/doc/38-aot.md}{LLVM AOT 编译}，不能只改文件后缀就把 Windows 程序当成 Linux 程序。

\section{调试与发布}

\par
\medskip
\begin{lstlisting}[style=sh]
chali aot app.chl --checked --debug --out build/app-debug
\end{lstlisting}
\par
\medskip

调试构建保留 DWARF 源码行、参数和局部变量信息，使用 O0；通过 VS Code 的 ChaLi 调试入口或 GDB 进行源码断点、单步和变量查看。发布构建继续使用最高优化、LTO 和死代码消除。详细设置见\href{https://github.com/rabbitc999/ChaLi/blob/master/doc/43-native-debugging.md}{原生 AOT 调试}。

发布前检查参数、输入输出、C ABI 库、资源清理及错误路径，并记录实际编译器版本、目标与产物摘要。原始 \texttt{.\allowbreak{}ll} 和四元式可用于分析，不必作为应用运行依赖交付。

\section*{小结}

开发时 \texttt{run} 使用 checked AOT；导出时 \texttt{aot} 默认 unchecked，需要时显式加 \texttt{--checked}。交付原生产物及应用依赖，不交付 VM 或已经删除的字节码格式。

\section*{习题}

前两题用于理解和基本实现，第三题检查边界，最后一题为综合挑战。先独立完成，再核对参考解答。

\begin{enumerate}

\item \texttt{run} 与 \texttt{aot} 的默认检查配置分别是什么？

\item 调试导出需要哪两个常用选项？

\item 为什么不能把跨架构编译器构建视为相应 AOT 目标已经验证？

\item 挑战：为 \texttt{app.\allowbreak{}chl} 分别产出 checked 调试产物与 unchecked 发布产物，并在另一台没有安装 ChaLi 的机器（或干净目录）上验证运行。

\end{enumerate}

\section*{参考解答与验收要点}

\begin{enumerate}

\item \texttt{run} 默认 checked，\texttt{aot} 默认 unchecked；后者可以显式使用 \texttt{--checked}。

\item \texttt{--checked --debug}：保留检查并生成原生调试信息。

\item 编译器能运行在某架构，不代表 LLVM 后端、运行时和链接资产已经支持或验证该目标。

\item 两条命令分别加 \texttt{--checked --debug} 与默认参数，各产出独立文件；验收时记录编译器版本、目标平台与产物摘要，确认目标机器无需编译器、VM 或 LLVM 动态库即可运行。

\end{enumerate}

\section*{番外：两份行李}

改编自《晏子使楚》。

晏子要出使邻国，楚王吩咐门吏：“晏子带着的行李，一定又多又乱。你们把他拦下，看看里面有没有违禁品。”

晏子只拎了两只箱子过境。第一只箱子贴着“checked”的封条：路上每一步都有人核对——数组不越界，指针不乱指，资源用完就归还。第二只箱子贴着“unchecked”：为了跑得快，封条只盖了启程那一站，路上的安全全凭先前查过的规矩。

楚王开箱验看，问：“为何不把所有箱子都贴上 checked？”晏子答：“开发时我步步核查，是怕自己写错；交付给别人的产物，默认轻装上阵，是因为规矩在出发前已经查过。真要严格，加一道封条就是了，不必把整个驿站搬进行李。”

楚王又问：“那你的行李里怎么还带一个随行的译官？”晏子说：“不需要。我的程序出发前就已编译成当地的原生机器码，落地即走，用不着把每句话现场再翻译一遍。”

门吏在关文上盖了章：两份行李，一封检查，一个落地即走的原生程序。

\subsection*{技术对照}

\texttt{run} 的 checked 与 \texttt{aot} 的 unchecked 是同一套语言规则下的两种交付形态，不是两套安全模型；unchecked 不允许绕过所有权或静态借用规则，只是运行期数组与指针检查的默认开关不同。原生产物在目标机器直接执行，不需要编译器、解释器或 LLVM 动态库随行。跨架构构建编译器不等于相应 AOT 目标已支持，部署前仍按实际目标验证。
