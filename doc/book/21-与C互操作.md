# 第 21 章 与 C 互操作

<!-- LANGUAGE NAVIGATION -->
[English](en/21-c-interop.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

到第 20 章为止，你的程序都活在自己的世界里。可现实中有太多东西是现成的 C 库：
压缩、加密、数据库、图形、系统调用……你不可能全都重写一遍。

这一章讲**怎么跨过 ChaLi 和 C 的边界**，两个方向：

- **ChaLi 调 C**——用 `#abi` 指令调动态库里导出的函数；
- **C 调 ChaLi**——把你的函数交给 C 的运行时。

---

## 21.1 三种集成方式

工具链支持三条路，按「需要多少 C 侧配合」排：

| 方式 | 用在哪 | 你要准备什么 |
| --- | --- | --- |
| `#abi` 指令 | 调**动态库**里按 C ABI 导出的函数 | 一份 `.dll` / `.so` |
| 函数值过边界 | ChaLi 把函数交给 C，C 在本次调用里同步回调 | 一个接收函数指针的 C 入口 |
| `--shared --export` | C 宿主调用 AOT 导出的动态库 | 生成的 `.h` 和加载代码 |

`#abi` 指令是**最轻**的一条——不用改工具链，不用重新编译，运行时直接加载库。

---

## 21.2 `#abi` 指令：调动态库里的 C 函数

假设你有一个 C 文件 `native.c`：

```c
#include <stdint.h>

#if defined(_WIN32)
#define CHALI_ABI_EXPORT __declspec(dllexport)
#else
#define CHALI_ABI_EXPORT
#endif

CHALI_ABI_EXPORT int32_t abi_add(int32_t left, int32_t right) {
    return left + right;
}

CHALI_ABI_EXPORT const char *abi_name(void) {
    return "native";
}
```

先把它编成动态库（说句实话：「怎么编动态库」是 C 的事，和 ChaLi 无关）：

```sh
gcc -shared -o native.dll native.c
```

然后在 ChaLi 里声明想用的函数：

<!-- dll tmp/abi21/native.c native.dll -->
```chali
#abi("C", "./native.dll", "abi_add")
int32 native_add(int32 left, int32 right);
#abi("C", "./native.dll", "abi_name")
String native_name();

void main()
{
    println("{} {}", native_add((int32)20, (int32)22), native_name());
}
```

```text
42 native
```

导入使用逐函数编译器指令：

```text
#abi("C", "<动态库路径>", "<库里的符号名>")
<返回类型> <ChaLi侧名字>(<形参表>);
```

**第三个参数是库里真实导出的符号名**，函数声明使用的是 ChaLi 中的本地名称。
两者可以不一样——给一批 C 函数起统一风格的 ChaLi 名，就靠它。

> 路径按**声明所在的源文件**解析。动态库本身要和产物放在同一目录——Windows 加载器在进程启动时
> 按 exe 目录和 `PATH` 找库，放别处就是「找不到 DLL」。

## 21.3 结构体、引用、字符串

标量只是热身。真实场景里你还要传**结构体**（按值）、**引用**（原地改）、**字符串**：

```c
API Point move_point(Point p, int32_t dx, int32_t dy) {
    p.x += dx; p.y += dy;
    return p;
}
API void bump(int32_t *value) { ++*value; }
API const char *greet(void) { return "hello from C"; }
```

ChaLi 侧：

<!-- dll tmp/abi21/abi_demo.c abi_demo.dll -->
```chali
struct Point
{
    int32 x;
    int32 y;
};

#abi("C", "./abi_demo.dll", "move_point")
Point move_point(Point p, int32 dx, int32 dy);
#abi("C", "./abi_demo.dll", "bump")
void bump(int32 mut& value);
#abi("C", "./abi_demo.dll", "greet")
String greet();

void main()
{
    Point p;
    p.x = 1;
    p.y = 2;
    Point q = move_point(p, (int32)10, (int32)20);
    println("{} {} / {} {}", p.x, p.y, q.x, q.y);

    int32 n = 41;
    bump(&n);
    println("{}", n);

    println("{}", greet());
}
```

```text
1 2 / 11 22
42
hello from C
```

三个要点：

1. **结构体按值传**——C 的 `Point p` 对应 ChaLi 的 `Point p`，布局默认按 C 规则对齐。
   所以 ChaLi 这边得**声明一个字段顺序、类型都一致的 `struct`**；
2. **C 的 `int32_t *value` 对应 `int32 mut& value`**（第 7 章的可变引用），
   调用处写 `bump(&n)`——**取地址用 `&`**，和 ChaLi 内部引用是同一套写法；
3. **C 的 `const char *` 对应 `String`**。

### 支持的类型一览

| ChaLi 写法 | 含义 |
| --- | --- |
| `int8`…`int64`、`uint8`…`uint64`、`float32`、`float64`、`bool` | 标量，按值传 |
| `String` | 字符串（C 侧 `const char *`） |
| `T mut&` / `T const&` | 可变 / 只读引用（C 侧 `T *` / `const T *`） |
| `Option<T mut&>` / `Option<T const&>` | **可空引用**（C 侧可以是空指针） |
| `T[]` + 另给长度 | 数组视图（C 侧 `T *`） |
| 结构体 | 按值传，默认 C 布局 |
| `struct X packed { … }` | 紧凑布局，对接 C 的 `#pragma pack` |

## 21.4 数组与「可空」：边界上的两个特殊话题

**数组**用 `T[]` 传，长度**单独给一个参数**；如果返回的数组长度由某个形参决定，
在末尾用 `[count]` 标注：

<!-- no-run -->
```chali
#abi("C", "./native.dll", "packed_numbers")
Packed[] packed_numbers(int32 count) [count];
#abi("C", "./native.dll", "packed_fill")
void packed_fill(Packed[] values, int32 count);
```

**「空」是这个边界上唯一允许出现空的地方。** ChaLi 内部的引用**永远非空**（第 7 章），
但 C 函数可能返回空指针。这时候用 `Option<T mut&>` / `Option<T const&>` 接：

<!-- no-run -->
```chali
#abi("C", "./native.dll", "packed_snapshot")
Option<Packed const&> packed_snapshot();
```

返回 `None` 就代表 C 那边给了个空指针；传参时也可以传
`Option<Packet mut&>::None`，C 侧收到的就是空指针。

> **这是「空」唯一能跨过边界的通道。** 跨过边界之后，一切又回到「引用非空」的老规矩。

`packed` 结构体用于对接 C 侧 `#pragma pack` 的紧凑布局——C 里用
`#pragma pack(push, 1)` 压过的地方，ChaLi 侧就声明成 `struct X packed { … }`。

完整例子见 [`doc/examples/abi_buffers/`](../../doc/examples/abi_buffers/)——
它覆盖了结构体嵌套、紧凑布局、数组读写、可空引用、返回值长度等全部边界情况。

## 21.5 同步回调：把 ChaLi 函数交给 C

反过来也成立：ChaLi 的函数值能当机器函数指针传给 C，C 在**这次调用期间**直接调它。

```c
/* host.c 里导出：拿到 fn，用它处理 value */
int64_t hostApply(int64_t (*fn)(int64_t), int64_t value) {
    return fn(value) + 1;
}
```

ChaLi 侧声明时把 `fn` 写成函数类型的形参，传一个普通函数进去：

<!-- no-run -->
```chali
#abi("C", "./host.dll", "hostApply")
int64 hostApply(int64 fn(int64) function, int64 value);

int64 twice(int64 x) { return x * 2; }

void main()
{
    println("{}", hostApply(twice, 21));
}
```

```text
43
```

能传的不只是具名函数。闭包也能过边界，捕获的数据由运行时带着走——C 侧看到的仍然只是
`int64_t (*)(int64_t)`，调用时它自然读到正确的捕获环境。传 `void`、`float32`、`bool`、
`int64 mut&` 形参的回调同理。

三条规矩：

1. **只能同步用**。函数值里的地址在这次调用期间、这条线程上有效；C 把它存进全局变量、
   过一会儿在别的线程上回调，就是野指针。
2. **`panic` 能穿过 C 帧**。ChaLi 回调里 panic 会一路回到顶层，按运行期错误报告，
   不会悄悄变成 `0` 让 C 侧继续算下去。
3. **别指望自动转移所有权**。`String`、`List`、`Map` 这些带资源的值不走这条路，
   要么在接口上用标量和引用，要么自己管缓冲区。

完整可运行版本（具名函数、内联 lambda、`copy` / `move` 捕获、`float32`、`bool`、`void`、
`int64 mut&`、重入）见[同步回调示例](../../example/native-callbacks/README.md)。

## 21.6 反方向：宿主调用 ChaLi

要 C 程序主动调 ChaLi，用 `--shared --export` 把函数导成动态库：

```sh
chali aot app.chl --out build/app --shared --export add
```

`build/app.h` 给出声明：

```c
void chali_init(void);
void chali_finish(void);
int64_t f_add(int64_t p0, int64_t p1);
```

宿主按三段顺序调用：`chali_init()` 分配运行期内存、装入数据区、跑全局初始化；然后调
`f_名字(...)`；最后 `chali_finish()` 做全局清理、刷新输出、释放内存。`chali_finish()`
之后原有句柄一律失效。

导出函数只接收和返回 C 标量；要传结构体就按值传，要原地修改就用 `T *` 对应的引用形参。
`panic` 会穿出 C 帧变成进程级错误，宿主看到的是非零退出而不是一个假返回值。

不导出任何函数、直接 `chali aot app.chl` 时，得到的是一个自包含可执行文件——那是交给
最终用户的形态，见[第 24 章](24-AOT导出.md)。

## 21.7 小结

| 你会了 | 关键点 |
| --- | --- |
| 三种集成 | `#abi` 指令（ChaLi 调 C）／函数值同步回调／`--shared --export`（C 调 ChaLi） |
| `#abi` 指令 | `#abi("C", "./x.dll", "C符号名") 返回类型 名字(形参);` |
| 名字映射 | 第三个指令参数是 C 侧真实符号名，声明使用 ChaLi 本地名称 |
| 结构体 | 按值传；ChaLi 侧声明字段一致的 `struct` |
| 引用 | C 的 `T *` ↔ ChaLi 的 `T mut&`，调用处写 `&x` |
| 字符串 | C 的 `const char *` ↔ ChaLi 的 `String` |
| 数组 | `T[]` + 长度另给；返回长度用 `[count]` 标注 |
| 「空」 | 只有 `Option<T &>` 能把空送过边界 |
| 紧凑布局 | `struct X packed { … }` 对接 `#pragma pack` |
| 函数值 | 直接当机器函数指针传，C 同步调用；只能本次调用、同线程用 |
| 反向 | `--shared --export` 出库 + 头文件，`chali_init` → `f_名字` → `chali_finish` |

## 21.9 边界与验证

ABI 一致只是互操作的前提之一。指针、字符串、回调上下文的拥有与有效期必须明确；同步回调靠函数值里的运行期地址，它只在这条线程、这次调用里有效，不能缓存成通用机器入口。

## 21.10 习题

前两题用于理解和基本实现，第三题检查边界，最后一题为综合挑战。先独立完成，再核对参考解答。

1. 为什么两边函数名相同仍可能无法安全调用？
2. 列出传入 UTF-8 字符串时宿主必须明确的三个约定。
3. 说明宿主保存一次同步调用的临时上下文为何可能出错。
4. 挑战：为一个宿主函数设计参数数目、返回类型和错误传播测试。

### 参考解答与验收要点

1. 还需要调用约定、参数宽度、布局、返回协议及生命周期一致。
2. 编码、长度或终止方式、缓冲区有效期与释放责任至少说明清楚。
3. 调用结束后上下文不再有效，后续使用不受原同步调用保证，需使用实际支持的长期注册协议。
4. 覆盖合法调用与不匹配调用，保留原始错误来源，检查没有把 VM 值地址强转成机器入口。

## 21.11 番外：借来的梨树与指针

改写自《聊斋志异·种梨》。

有乡人货梨于市，颇甘芳，价腾贵。有道士求一梨，乡人叱之。旁人买而赠焉。道士食尽，留核，掘地埋之，俄而一树，枝叶扶疏，累累有梨，请众人任取。

乡人看得心热，忙将树的位置记在纸上，欲待散场，日日来摘。道士斫树而去，乡人依旧址伸手，只抓得一把尘土。乃怒曰：“这地址未变，梨何故不在？”

道士回身曰：“君记住地址，未曾取得所有权。对象既去，地址尚存，有何稀奇？”乡人仍不服，把旧指针换一个更大的整数，以为范围变宽，梨便能多活几天。

旁一木匠接过枝条，约定只在眼前加工。乡人又将这口头保证写成永久回调，待人散尽，遥唤木匠，哪还有上下文应答？

道士指着三个字教他：“谁创建，谁释放；借多久，何时用。跨语言的墙，挡不住生命周期的账。”

乡人回看梨车，梨已尽失，连车把也不知去了哪里。他捏着那张地址单，终于明白：ABI 对上，不过说明门牌格式认得；门后有没有人、谁有权搬家，仍须另外说清。

ABI 一致只是互操作的前提之一。指针、字符串、回调上下文的拥有与有效期必须明确；同步回调靠函数值里的运行期地址，它只在这条线程、这次调用里有效，不能缓存成通用机器入口。
