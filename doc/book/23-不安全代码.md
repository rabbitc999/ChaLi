# 第 23 章 不安全代码与原始存储

<!-- LANGUAGE NAVIGATION -->
[English](en/23-unsafe-code.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

实现容器或宿主适配时，需要区分“有一块空间”和“其中已经构造了值”。容量、初始化状态、地址步长和清理责任若混在一起，就容易把字节写入误作对象构造，或把已移出的元素再次清理。

本章依次说明 unsafe 调用范围、RawStorage 的槽位状态、BarePtr 的地址运算，以及字节复制与值复制的区别。每个例程都围绕具体前提展开，最终目标是把这些操作封装成外部可安全使用的接口。

## 23.1 地址不是任意有效对象

在低层代码中，地址可以表现为一个数，但一个数并不能证明那里有可读取的对象。即使加法算对，还要说明分配是否有效、偏移是否在范围内、布局和对齐是否符合访问类型。

先用一个只做整数加法的 unsafe 函数说明调用范围。std::lang::address 等地址查询也需要结合其接口理解；本节刻意不解引用计算结果，后面再逐步引入有分配来源的存储与指针。

<!-- verify-book -->
```chali
unsafe int64 addOffset(int64 address, int64 bytes) {
    return address + bytes;
}

void main() {
    unsafe {
        println("{}", addOffset(100, 8));
    }
}
```

```text
108
```

### 代码详解

addOffset 被声明为 unsafe 函数，调用者必须在允许不安全操作的范围内调用。main 用 unsafe 块包住调用，传入两个整数 100 与 8，函数只做加法，因此输出 108。

这个例程没有把 108 解引用，也没有证明地址 100 对应有效分配。它用简单运算展示调用权限，不能当成安全的真实地址访问示例。unsafe 把额外前提留给作者，不等于取消整个程序的类型、边界和存活规则。


## 23.2 原始容量与初始化状态

RawStorage<T> 分配容量但不构造全部元素。initAt 在未初始化槽位构造值，takeAt 移出并使槽位重新未初始化，dropAt 清理存活元素但保留容量。清理时不能把同一拥有值析构两次。

<!-- verify-book -->
```chali

void main() {
    RawStorage<String> slots = RawStorage<String>::allocate(4);
    unsafe {
        initAt<String>(slots.pointer(0), "hello");
        String result = takeAt<String>(slots.pointer(0));
        assert(!slots.isInitialized(0));
        println("{} / {}", result, slots.capacity());
    }
    slots.close();
}
```

```text
hello / 4
```

### 代码详解

allocate(4) 为四个 String 槽位预留容量，但不构造四个字符串。initAt 在下标 0 建立 hello，takeAt 随后把这个拥有值移给 result，并把槽位重新标为未初始化；assert 核对这一状态变化。

移出不缩小容量，因此打印 hello 与 4。slots.close 释放原始分配时不应再次清理已经移出的字符串；result 作为独立拥有值按自身作用域清理。重复 takeAt 或在未重新 initAt 前读取槽位都不符合状态要求。容量、已初始化元素和已移出的值需要分别跟踪。


<!-- verify-book -->
```chali

void main() {
    RawStorage<int64> slots = RawStorage<int64>::allocate(3);
    unsafe {
        BarePtr<int64> p = barePointer<int64>(slots.pointer(0));
        BarePtr<int64> q = p + 2;
        assert(q.address - p.address == 16);
        assert((2 + p).address == q.address);
        q = q - 1;
        println("{} / {}", q - p, q.address - p.address);
    }
    slots.close();
}
```

```text
1 / 8
```

### 代码详解

p 从带分配信息的指针取得 BarePtr<int64> 视图，q=p+2 按元素步长前进，不是只加两个字节。本例 int64 步长为 8 字节，所以地址差为 16；第二个 assert 核对整数在左侧的相加也得到相同位置。

q 再减 1 后，与 p 相差一个元素，原始地址相差 8 字节，打印 `1 / 8`。这里仅做地址计算，没有读取未初始化整数。BarePtr 不拥有存储，也不会延长 slots 的寿命，close 之后这些地址不能继续作为有效访问来源。


## 23.3 复制字节与复制值

memcpy 等原语只按其内存约定工作，不能普遍替代拥有型对象的复制操作。按字节复制整数和按字节复制 String 的拥有信息不是同一回事；后者可能破坏所有权、引用计数或清理状态。

<!-- verify-book -->
```chali

void main() {
    RawStorage<int64> source = RawStorage<int64>::allocate(1);
    RawStorage<uint8> target = RawStorage<uint8>::allocate(8);
    unsafe {
        BarePtr<int64> from = barePointer<int64>(source.pointer(0));
        BarePtr<uint8> to = barePointer<uint8>(target.pointer(0));
        memset<int64>(from, (uint8)42, 8);
        memcpy<uint8,int64>(to, from, 8);
        uint8 mut& first = dereference<uint8>(to);
        uint8 mut& last = dereference<uint8>(to + 7);
        println("{} / {}", (int64)*first, (int64)*last);
        assert(!source.isInitialized(0));
    }
    source.close();
    target.close();
}
```

```text
42 / 42
```

### 代码详解

source 预留一个 int64 的空间，target 预留八个 uint8 的空间。memset 的数值 42 是逐字节填充值，长度 8 的单位也是字节；它不是向 source 构造整数 42。随后 memcpy 将这八个字节复制到 target，读取首尾 uint8 都得到 42。

即使实际字节已被写过，source 的类型化初始化位仍未建立，assert 因而确认 isInitialized(0) 为假。这区分了“写入原始内存”和“构造一个 T”。示例只针对这些整数／字节视图，不应把同样方式套在拥有 String 等资源的对象上；退出时仍分别关闭两块存储。


## 23.4 封装和验证不变量

在安全入口验证数量和边界，在内部维护已初始化区间，在退出路径清理实际存活元素。rawSize 描述对应查询的原始存储大小，不能据此假定宿主 ABI、所有对齐或任意序列化格式。完整边界见 [不安全存储与 ABI](../41-unsafe-abi.md)。

### 小结

跟踪原始存储时记录分配范围、元素布局、逐槽状态和借用。initAt 建立元素，takeAt 移出元素，dropAt 清理元素，close 释放整个存储；裸字节操作不会自动维护同一套类型化状态。

地址相同或数值落在区间内，都不能单独证明某种类型访问合法。应让安全入口检查可检查的条件，让内部实现维护剩余不变量，并对失败与退出路径保留真实验证。随后进入 AOT 交付，把程序与运行环境一起核对。

3. 为何 memcpy 不能替代所有复制？
4. 封装原始存储时应记录哪些状态？

2. 不会，清理该元素并保留容量。
3. 拥有值包含清理和所有权语义。

## 23.6 番外：油杓与葫芦

改写自欧阳修《卖油翁》。

陈尧咨见老翁酌油，问道：“既然手熟，何必还要铜钱？”翁曰：“钱孔使我看清边界，手熟使我守住边界，二者并不相妨。”

有门客闻言，将铜钱收进袖里，又在葫芦上贴了“不安全”三字，自谓已尽得要领。油未入瓶，先湿了衣袖。公问其故，门客答：“既已声明不安全，自然可以不问油流向哪里。”

翁取杓而止之：“你可以亲手持杓，却不能把别人的葫芦当作自己的。倒进去的是油，不是瓶子的主人；抄下来的是瓶号，也不是第二只瓶子。”

于是门客把取油、持杓、换瓶各写一条规矩，替客人留下一个稳妥的把手。客人只须接过葫芦，如何守住钱孔，仍由持杓的人负责。公笑曰：“这回写在纸上的，终于不是免罪的告示。”

### 技术对照

`unsafe` 表明实现者承担额外证明义务。裸地址和按位复制不会产生资源所有权，范围检查与清理协议仍各有职责。把底层操作封装成接口，是让调用者使用已经维护好的不变量；性能则要通过实际负载检验，不能由一个关键字推断。
