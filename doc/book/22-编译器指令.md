# 第 22 章 指令与派生行为

<!-- LANGUAGE NAVIGATION -->
[English](en/22-compiler-commands.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

部分类型行为需要编译器参与，例如按字段生成相等与哈希，或把返回引用与特定参数来源连接起来。指令为这些特殊机制提供入口，但它们仍需与普通类型和所有权规则一致。

本章先通过派生观察复制后的关系，再比较运算替代方向，最后追踪 #borrow 的返回来源。阅读时从指令实际影响的行为出发，不把“加了标记”当成可以跳过其他检查的理由。

## 22.1 派生相等、哈希和复制

两个坐标值怎样判断相等，复制后是否保持内容，作为键时如何计算哈希，这些行为常常由字段结构重复定义。支持的 #derive 指令可以为类型建立对应实现，让调用者按协议使用。

下面对 Point 请求 Equal、Hash、Clone，再先比较副本、后改变一个字段。这样不只看到指令写法，还能观察各行为如何与普通值语义连接。现有派生不等于已经开放任意自定义声明宏。

<!-- verify-book -->
```chali
#derive(Equal, Hash, Clone)
struct Point
{
    int64 x;
    int64 y;
    String label;
};

void main()
{
    Point origin;
    origin.x = 0;
    origin.y = 0;
    origin.label = "O";

    Point copy = origin.clone();
    println("equal={}", origin == copy);
    println("sameHash={}", origin.hash(origin) == copy.hash(copy));

    copy.label = "O2";
    println("afterChange={}", origin == copy);
    println("original={}", origin.label);
}
```

```text
equal=1
sameHash=1
afterChange=0
original=O
```

### 代码详解

Point 的三个字段都参与派生行为。origin 初始化为坐标 0、0 和标签 O，clone 后 copy 的内容相等，因此 equal 与 sameHash 都为真。后一个检查比较的是两个哈希结果，不是在验证一个固定哈希常量。

把 copy.label 改为 O2 后，坐标虽然仍相同，字段整体已不同，afterChange 为假；origin.label 仍为 O，说明修改副本没有写回原字符串。相等对象需要一致哈希，但哈希相等不能反证内容相等，也不适合直接作为持久化身份。


## 22.2 运算替代与接收关系

自定义运算需要明确左右操作数、返回类型以及是否修改接收者。下面分别观察禁止复合替代和禁止右操作数替代后的结果；不要根据熟悉的符号假定所有类型都遵循内建数值的转换。

<!-- verify-book -->
```chali
#NoAddReplace
struct Vec : Add<int64, int64>
{
    int64 v;

    int64 leftAdd(int64 other)
    {
        return self.v + other;
    }
};

void main()
{
    Vec a;
    a.v = 10;
    println("left={}", a + 5);
}
```

```text
left=15
```

### 代码详解

Vec 实现 Add<int64, int64>，由 leftAdd 接收右侧整数并返回整数结果。表达式 a+5 选择这个行为，以 a.v=10 计算 10+5，打印 left=15；它没有把 a 的类型转换为 int64。

#NoAddReplace 限制的是相关替代行为，不会删除本例显式实现的左侧加法。函数体只读取 self.v，因此这次加法也没有修改 a.v。不要从 a+5 合法推断 a+=5、5+a 或其他组合都合法，它们需要各自满足接口和指令约束。


<!-- verify-book -->
```chali
#NoRightAdd
struct Chain : Add<int64, int64>
{
    int64 v;

    int64 leftAdd(int64 other)
    {
        return self.v + other;
    }
};

void main()
{
    Chain chain;
    chain.v = 7;
    println("chain + 1 = {}", chain + 1);
}
```

```text
chain + 1 = 8
```

### 代码详解

Chain 同样提供 leftAdd，chain.v 为 7，因此 chain+1 调用方法得到 8。#NoRightAdd 约束的是右操作数替代方向，这里 Chain 处在左侧，仍走已有左加法。

本例刻意只执行合法方向，不包含 1+chain 的正例；不能把交换两个操作数当成无需检查的代数变换。对于自定义类型，接收者、结果类型和副作用都由接口实现决定，熟悉的加号并不自动承诺交换律。


## 22.3 借用来源声明

#borrow 描述返回借用与输入来源之间的关系，让调用者能按正确存活范围使用结果。它不能让已经销毁的对象继续存活，也不能取消重叠可变访问的限制。

<!-- verify-book -->
```chali
#borrow(#ret, [a])
int64 mut& first(int64 mut& a, int64 mut& b)
{
    return a;
}

int64 mut& outer(int64 mut& x)
{
    int64 local = 5;
    return first(&x, &local);
}

void main()
{
    int64 number = 30;
    int64 mut& selected = outer(&number);
    selected = 31;
    println("{} {}", number, selected);
}
```

```text
31 31
```

### 代码详解

#borrow(#ret, [a]) 说明 first 返回的借用只来自 a。虽然它也接收 b，函数体实际上直接 return a，因此调用方不必把返回值的寿命绑定到所有形参来源。

outer 传入外部 x 与局部 local，返回值仍追溯到 x，所以 local 退出不使结果失效。main 的 selected 最终指向 number，赋值 31 写回同一个对象，输出两项都是 31。来源声明必须符合实现；它不是让函数可以谎报来源，也不能把 local 的实际引用伪装成外部借用。


## 22.4 选择最小的特殊机制

普通方法能表达的业务规则先写普通方法。资源关闭见第 8 章，反射见第 20 章，C ABI 见第 21 章；把不同机制的约束放在各自边界检查，而不是堆叠指令后依靠试跑猜测含义。

### 小结

派生减少已有协议的重复实现，运算指令限定替代范围，借用来源说明结果依赖哪一个输入。每个机制都要结合实际函数体和调用位置核对，不能靠一个成功输出推断所有组合都有效。

优先让普通方法表达业务；需要特殊机制时再选择最小的指令。下一章的不安全操作同样要求明确前提，只是其中更多义务由实现者负责证明。

## 22.6 番外：一张便条的权力

改写自刘禹锡《陋室铭》。

指令不在多，入语义则灵；注解不在长，有元数据则明。斯是声明，惟约定清。`#NonCopyable` 上类型，普通赋值莫偷行；谈笑皆诊断，往来无蒙混。可以查文法，验类型。无乱标记之扰眼，无假接口之劳形。

编译器阅此处，反射者查彼层。一个管能不能做，一个记身上有什么名。若将禁止复制只写成一条注解，便似在库门贴“请勿搬走”，看门人却从未接到命令。

主簿有言：“何陋之有？”差役答曰：“陋倒不陋，就是把便条当成了律令。”

县令闻之，命贴一千张“本库绝不失窃”，以为从此安全。次日失物，差役按注解查出每一只空箱的名称，竟无一项阻止了搬运。县令大怒，要追加一个 `@ReallyReallySafe`。主簿将笔夺下，曰：“再加一个 Really，也不会自动生成一条检查。”

于是语义约束写入指令，描述信息留给注解。库中少了九百九十九张告示，规矩却第一次真正执行起来。县令大喜，欲为主簿加注“善治”。主簿再三说明：这个倒可以，只求别指望它自动发俸禄。

### 技术对照

指令与注解的关键差别在读取者：指令由词法与语义层读取，参与类型检查；注解由反射在运行期读取，
不改变语义。把"禁止某条推导"这类声明级约束写成标记接口，等于把规矩写进借条里。
