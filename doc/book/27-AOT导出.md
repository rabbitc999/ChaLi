# 第 27 章 AOT 导出：把程序交付为原生产物

<!-- LANGUAGE NAVIGATION -->
[English](en/27-aot-export.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

运行一个开发例程与交付一个可部署程序，涉及不同层次的证据。AOT 生成目标机器代码，但目标库、系统加载器、动态依赖与资源目录仍要匹配，不能以“文件已经生成”作为全部验收。

本章从 run 与 aot 的默认配置开始，串起前端、四元式与 LLVM 后端，再区分工具链和应用依赖，说明交叉编译、原生调试与分阶段部署。阅读配置时始终注明宿主、目标和实际执行到哪一步。

## 27.1 运行与导出的配置

先区分两个目的：开发时立即看到程序行为，交付时生成指定环境的原生产物。run 将编译与执行连在一起，默认 checked AOT；aot 用于导出，默认 unchecked，LLVM 优化等级默认 O3。

unchecked 的相关默认开关主要影响运行期数组与指针检查，静态类型、所有权和借用检查仍然存在。比较两次执行时，把这些配置也写进记录，不只比较源码文件是否相同。

命令选项以 chali help 和 [LLVM AOT 文档](../38-aot.md) 为准。不要再使用已删除的 emit 或 .svmb 路径。

![AOT 导出与工具链边界](images/chali-aot.png)

### 从源码走到原生执行

先把处理过程分成前端、四元式、LLVM IR 和目标产物几个层次。前端解析声明与表达式，并进行名称、类型、所有权和借用检查；宏也在编译阶段展开。ChaLi 四元式表达语言操作，后端再将这些操作降低为 LLVM IR。LLVM 负责优化和目标代码生成，链接步骤把对象与所需运行时、系统库和应用依赖组合成原生产物。

本书不加限定的 IR 指 ChaLi 四元式；LLVM IR 则明确写全，两者不能互换。当前内部四元式优化遍与聚合优化已经删除，优化交由 LLVM 的 O3／LTO 路径处理。不能从旧版四元式优化说明推断当前仍会运行那些遍，也不能从 O3 推断每一种程序都获得同样收益。

run 是把编译与执行组合起来的入口，采用 checked AOT，并非在 VM 中逐条解释四元式。当前编译器及内嵌资产不含 VM 解释执行核，旧 .svmb 导出也已删除。开发时用 run 验证的程序，正式导出时仍应核对目标、检查开关和链接配置；两次命令的默认配置并不完全相同。

checked 有助于在运行时发现相应的非法访问，静态检查则在运行前拒绝不合法程序。两层检查各有覆盖范围，任何一种都不能证明业务输入必然有效。选择 unchecked 时应理解具体开关，并对发布配置做实际验收；不要只因开发配置通过就省略发布产物的运行检查。

## 27.2 工具链依赖与应用依赖

内置 LLVM 变体携带编译所需组件，外置变体使用已安装工具链。两者生成的应用按实际链接结果交付；编译器使用 LLVM 不等于应用必须携带 LLVM 动态库。

应用主动调用的 C ABI 动态库、数据库客户端和运行期资源仍按各自约定准备。对最终文件检查真实依赖，不从编译器变体名推断。

## 27.3 交叉编译需要哪些信息

交叉编译至少要明确目标 triple、CPU／特性、目标 ABI、sysroot、链接器、目标运行库与启动资产。可将受支持配置写入 toml；具体键与命令行覆盖规则按 [AOT 配置参考](../38-aot.md) 使用，不把宿主库路径混入目标链接。

```toml
[aot]
target = "aarch64-unknown-linux-gnu"
cpu = "generic"
sysroot = "build/cross-sdk/linux-arm64/sysroot"
runtime_dir = "build/cross-sdk/linux-arm64/lib"
output = "executable"
```

[aot] 将这些键归入导出配置。target 选择 ARM64 Linux GNU 目标，cpu=generic 不针对某一具体处理器调优；sysroot 指向目标系统头文件与库所在的根，runtime_dir 指向该目标所需运行时链接资产，不能用宿主 Windows 库代替。

output=executable 记录希望得到可执行产物，但这份配置不会下载 SDK，也不会凭空提供缺失库。两个路径相对于 chali.toml 解析，所以应把配置文件位置也纳入工程记录。后续命令若显式选择对象输出，会覆盖对应导出设置；配置意图与实际执行步骤应一起核对。


```sh
chali aot app.chl --target linux-arm64 --emit-obj --out build/arm64/app
```

aot 以 app.chl 为输入，--target 选择命名目标 linux-arm64，--out 指定输出位置。最关键的是 --emit-obj：该命令到对象文件生成就停止，尚未把目标运行库和启动资产链接为可执行程序。

因此这条命令适合单独验证目标代码生成，不能马上在 Windows 上执行得到的 ARM64 对象，也不能据它宣称目标设备已运行。下一步要用匹配的目标链接环境形成应用，再在目标系统验证启动与业务。输出路径应与其他架构隔离，避免混用同名对象。


路径相对 chali.toml 解析，命令行显式选项覆盖对应配置。上述 --emit-obj 只生成对象文件，不执行目标链接。

生成某架构对象文件不等于已经得到可部署应用。对象生成、目标链接和目标设备运行需要分别验收；构建出交叉架构编译器也不表示全部 AOT 目标自动可用。

## 27.4 部署核对与诊断

在干净目录核对配置文件、网页、动态库、数据目录权限及工作目录。首次启动先验证一个无副作用操作，再测试真实业务。需要原生调试时使用 DWARF 与 GDB/MI 路径；保留符号和错误日志，使用户能定位失败阶段。

### 按失败阶段收集证据

解析或类型检查失败时，还没有可供调试的目标程序，应先根据源码诊断修正输入。对象生成成功但链接失败时，应检查目标 ABI、库的架构、符号和搜索路径。程序链接成功却无法启动时，再检查操作系统加载器、动态库、资源路径与权限。程序启动后业务结果错误，则需要结合输入、日志和原生调试定位。文件已经存在只能证明某个步骤写出了文件，不能替代后续阶段的证据。

原生调试使用 DWARF 调试信息与 GDB/MI。调试信息帮助把机器指令关联到源码，但优化可能内联函数、合并操作或使局部变量难以直接观察。排查时保留被测二进制与对应源码、构建配置和符号，避免拿另一次构建的行号解释当前文件。调试入口及平台要求见[原生 AOT 调试](../43-native-debugging.md)。

交付前可把验收写成一条可复现的操作链：在目标环境准备依赖，进入约定工作目录，启动发布产物，完成一次读取，再完成一次有权限的写入并核对结果。涉及数据库时，同时验证连接失败和权限不足的诊断。验证记录写明宿主、目标、编译器变体与实际执行到的步骤；只在 Windows 上生成 Linux 对象文件，应报告对象生成成功，不能写成 Linux 部署验证通过。

运行时共享核心要求 C++17 与操作系统服务，面向桌面及受支持的嵌入式 Linux 宿主，不承诺裸机支持。目标 triple 只描述目标的一部分，不能替代目标系统的库、启动资产和真实设备验证。

### 小结

开发时通过 run 观察 checked 原生执行，发布时按实际 aot 配置验证产物。编译器自带哪些 LLVM 组件、应用依赖哪些库、目标上能否启动，是三个需要分别回答的问题。

交付记录保留命令、源码和二进制身份、目标环境及业务结果。对象生成、链接成功和目标运行都写明各自证据，不把前一步扩大成后一步。第 29 章将这些要求用于带网页与数据库的完整应用。

## 27.6 番外：行囊里的工具

改写自欧阳修《卖油翁》。

陈康肃公善导出，当世无双，公亦以此自矜。尝于家圃编译，有卖油翁释担而立，睨之，久而不去。见其原生产物十发十中，但微颔之。

康肃问曰：“汝亦知 AOT 乎？吾静态 LLVM，不亦精乎？”翁曰：“无他，但工具装得熟尔。”康肃忿然曰：“尔安敢轻吾后端！”

翁曰：“以我酌油知之。”乃取一葫芦，置于地，以钱覆口，徐以杓酌油沥之，自钱孔入，而钱不湿。因曰：“工具在我担中，亦可借隔壁工坊；油入葫芦之后，买油人岂须背着我的油杓回家？”

康肃悟，谓内置 LLVM 是将编译所需工具纳入编译器，外置 LLVM 是借工具链完成同样工序；导出应用不因此平白多带一个 LLVM DLL。

翁将行，又折回道：“不过，若你葫芦上还接着别人家的水管，莫因油杓已收，就说水管也不必交付。”公视之，果有一条自己声明的 C ABI 动态库依赖。

康肃笑而遣之，归来便将发布说明分成工具链依赖与应用依赖两栏。门客称赞文档更长了，公曰：“我宁愿多写两行，也不愿用户半夜来问，油有了，葫芦为什么打不开。”

### 技术对照

内置 LLVM 编译器把优化器、代码生成器、链接器和链接资产装进行囊；外置变体借助独立工具链完成这些步骤。交付的原生产物包含所需的 AOT 运行时，应用额外使用的 C ABI 库则按各自的链接约定准备。工具放在哪里与应用依赖哪些库，是两个需要分别核对的问题。
