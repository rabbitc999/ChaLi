# 第 16 章 错误处理与传播

<!-- LANGUAGE NAVIGATION -->
[English](en/16-errors.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

查询没有结果与执行遇到错误，都是正常程序需要表达的情况。用一个特殊整数或空字符串同时承担所有失败含义，容易把合法数据与异常状态混淆。Option 与 Result 把状态和载荷一起交给类型系统。

本章先用查找区分 Value 与 None，再处理接口错误、嵌套载荷和 ? 传播，最后用自定义 Try 说明传播协议。阅读时先看外层状态，再看载荷类型，才能判断程序继续计算还是提前返回。

## 16.1 Option 与 Result 的分支

在列表里找一个分数，可能找到，也可能没有。返回 0 无法说明是哪一种情况，因为 0 本身也可能是有效分数。Option<int64> 把“有一个整数”和“没有结果”分成 Value 与 None，让调用方必须按实际情况使用它。

下面先在 findFirst 中建立这两条返回路径，再比较三种读取方式：已知存在时 unwrap、缺失时采用后备值的 unwrapOr，以及把两种情况写明的 match。

<!-- verify-book -->
```chali
Option<int64> findFirst(List<int64> xs, int64 target)
{
    for (int64 x in xs)
    {
        if (x == target)
        {
            return Value(x);
        }
    }
    return None;
}

void main()
{
    List<int64> xs;
    xs.push(3);
    xs.push(7);
    println("{}", findFirst(xs, 7).unwrap());
    println("{}", findFirst(xs, 9).unwrapOr(-1));
    match (findFirst(xs, 3))
    {
        Value(v) => { println("found = {}", v); }
        None => { println("no"); }
    }
}
```

```text
7
-1
found = 3
```

### 代码详解

findFirst 返回 Option<int64>，用 Value 表示找到的值，用 None 表示没有结果。循环遇到匹配项就 return，不再继续扫描；如果遍历结束仍没匹配，才返回 None。列表作为按值参数传入，这里只读，不把它当作可写来源。

第一次查 7 确实找到，因此 unwrap 得到 7；第二次查 9 没找到，unwrapOr(-1) 使用后备值。第三次查 3，通过 match 在 Value 分支绑定 v 并打印。unwrap 要求存在值，match 和 unwrapOr 则显式覆盖缺失情况；不要把 -1 当成 Option 内部实际存入的结果。


## 16.2 枚举载荷中的接口匹配

对于 Result<String, Error>，普通成功载荷直接写 Ok(text)。错误载荷需要区分实现时，可以写 Err(IoError e)，单载荷变体也支持 Err::IoError(e)。在可唯一解析、不与变体或其他候选冲突时，还可以省略外层写 IoError(e)。剩余错误用 Err(_) 或 Err(_ other) 接收。

这些省略语法仅用于单载荷变体；多个载荷必须保留外层变体和括号内类型标注。不能凭一个类型名猜测它对应多个载荷中的哪一项。

<!-- verify-book -->
```chali
import std::io;
Result<String, Error> readDemo()
{
    return Result<String, Error>::Err(std::io::IoError::ReadFailed("demo"));
}
void main()
{
    let result = readDemo();
    match (result)
    {
        Ok(text) => { println("{}", text); }
        Err::std::io::IoError(e) => { println("qualified: {}", e.toString()); }
        Err(_) => { println("other error"); }
    }
    match (result)
    {
        Ok(_) => { println("ok"); }
        std::io::IoError(e) => { println("short: {}", e.toString()); }
        Err(_) => { println("other error"); }
    }
}
```

```text
qualified: 读取失败：demo
short: 读取失败：demo
```

### 代码详解

readDemo 不访问真实文件，而是直接构造一个 Err，载荷具体类型为 IoError，外层错误类型为 Error 接口。两个 match 都读取这个失败结果，Ok 分支不会执行。

第一次用 `Err::std::io::IoError(e)` 同时表达失败分支与具体类型，第二次用允许的简写 `std::io::IoError(e)`。两者都得到相同错误文本，但打印不同前缀，证明命中了各自的具体错误分支。保留 Err(_) 是为了处理其他 Error 实现，不能把一个 IoError 分支当成覆盖全部可能错误。


两个载荷保留外层 Failed(code, Type value)。当 Ok 和 Err 都可能带同一个接口实现时，显式变体区分标签，避免省略后出现歧义。

<!-- verify-book -->
```chali
import std::io;
enum Response
{
    Pending,
    Failed(int64 code, Error error)
};
void main()
{
    let response = Response::Failed(503, std::io::IoError::Closed);
    match (response)
    {
        Response::Pending => { println("pending"); }
        Response::Failed(code, std::io::IoError e) => { println("{}: {}", code, e.toString()); }
        Response::Failed(code, _ other) => { println("{}: {}", code, other.toString()); }
    }
    Result<Error, Error> result = Result<Error, Error>::Ok(std::io::IoError::Closed);
    match (result)
    {
        Ok(std::io::IoError e) => { println("ok: {}", e.toString()); }
        Ok(_) => { println("other success"); }
        Err(std::io::IoError e) => { println("err: {}", e.toString()); }
        Err(_) => { println("other failure"); }
    }
}
```

```text
503: 文件已关闭
ok: 文件已关闭
```

### 代码详解

Response::Failed 有两个载荷，先是 code，再是 Error。匹配时既绑定 503，又要求第二项具体为 IoError，因此本次进入专用分支；`_ other` 则为其他错误实现提供一个仍可调用接口方法的绑定。

后半段刻意构造 `Result<Error, Error>::Ok(...)`：虽然成功载荷的类型也叫 Error，外层状态仍是 Ok。它会命中 Ok 中的 IoError 模式，而不是 Err。阅读这类嵌套匹配时先确认外层成功／失败或枚举变体，再判断内层具体类型，不能仅凭载荷是错误对象就推断操作失败。


## 16.3 传播时的接口提升

? 在成功路径取得内部值，在失败或缺省路径按传播协议提前返回。若内部错误 IoError 实现了返回位置所需的 Error，Result<..., IoError> 可以向 Result<..., Error> 传播。Option 的接口载荷和自定义传播协议同样需要满足目标类型及协议约束，不能借 ? 跳过类型检查。

leaf 的具体 IoError 通过 ? 提升为外层 Error。Option 的成功载荷也能转为接口值；缺省路径仍由 ? 的 Option 协议处理。

<!-- verify-book -->
```chali
import std::io;
Result<String, std::io::IoError> leaf()
{
    return Result<String, std::io::IoError>::Err(std::io::IoError::Closed);
}
Result<String, Error> readName()
{
    String name = leaf()?;
    return Result<String, Error>::Ok(name);
}
Option<std::io::IoError> optionalError()
{
    return Option<std::io::IoError>::Value(std::io::IoError::Closed);
}
Option<Error> widenedError()
{
    let error = optionalError()?;
    return Option<Error>::Value(error);
}
void main()
{
    match (readName())
    {
        Ok(name) => { println("{}", name); }
        Err(std::io::IoError e) => { println("result: {}", e.toString()); }
        Err(_) => { println("other error"); }
    }
    match (widenedError())
    {
        Value(std::io::IoError e) => { println("option: {}", e.toString()); }
        Value(_) => { println("other value"); }
        None => { println("absent"); }
    }
}
```

```text
result: 文件已关闭
option: 文件已关闭
```

### 代码详解

leaf 总是返回 IoError::Closed 失败。readName 中 `leaf()?` 遇到 Err 就提前从当前函数传播失败，因此不会执行后面的 Ok(name)；返回接口错误时仍保存可识别的具体 IoError，所以 main 能匹配并打印它。

optionalError 返回的却是 Value，虽然其中也装着一个错误对象。widenedError 的 ? 因而成功取出该值，转换到 Error 接口并重新包进 Value，main 打印 option 前缀。这里 ? 判断的是容器的分支状态，不是载荷名称；Result 的 Err 与 Option 的 None 才是各自的提前退出路径。


## 16.4 自定义传播与恢复边界

自定义 Try 协议需要同时定义成功结果与残余状态如何转换。把恢复放在能做出决定的位置：文件错误可以重试或显示路径，业务错误可以返回字段提示，未知实现保留统一错误显示。清理规则继续适用于提前返回。

<!-- verify-book -->
```chali
enum Step: Try<int64, NoneResidual>
{
    Value(int64 value), Empty;
    TryBranch<int64, NoneResidual> branch()
    {
        match (self)
        {
            Step::Value(value) =>
            {
                return TryBranch<int64, NoneResidual>::Continue(value);
            }
            Step::Empty =>
            {
                return TryBranch<int64, NoneResidual>::Break(NoneResidual::None);
            }
        }
        panic("unreachable");
    }
};
Option<int64> addOne(Step step)
{
    int64 value = step?;
    return Option<int64>::Value(value + 1);
}
void main()
{
    println("{} {}", addOne(Step::Value(4)).unwrap(), addOne(Step::Empty).isNone());
}
```

```text
5 1
```

### 代码详解

Step 自己实现 Try<int64, NoneResidual>，由 branch 把业务状态转换成传播协议。Value 分支返回 Continue(value)，允许调用方继续；Empty 返回 Break(NoneResidual::None)，说明没有可继续的整数。末尾 panic 不是预期正常路径，本例两种变体都已在 match 中处理。

addOne 中的 step? 调用这套协议：输入 Value(4) 时提取 4，构造 Option::Value(5)；输入 Empty 时提前产生缺失结果，不再执行加一。main 对前者 unwrap 得到 5，对后者 isNone 得到真。自定义 ? 需要完整且类型相容的协议，不能只声明一个同名方法就任意传播控制流。


### 小结

Option 回答有没有值，Result 回答成功还是失败，接口载荷再说明具体内容。unwrap 依赖已建立的前提，match 展示完整处理路径，? 按协议把不能继续的状态交回当前函数的调用者。

业务代码要决定在哪一层补默认值、在哪一层保留错误信息。不要将所有失败吞成同一个字符串，也不要把含 Error 对象的成功载荷误作失败。接下来在迭代器中再次观察 Option 如何表达结束。

## 16.5 习题

1. 把 Err(_) 改成带名字的回退。
2. 何时能省略外层 Err？
3. 两个载荷的错误分支应如何标注接口类型？
4. ? 是否能把无关错误类型自动当成 Error？

### 参考解答与验收要点

1. 使用 Err(_ other)，再调用 other.toString()。
2. 单载荷且解析唯一，没有变体或类型候选冲突。
3. 保留变体，例如 Failure(code, IoError error)。
4. 不能，必须实现对应接口并满足传播协议。

## 16.6 番外：错误又来了

改写自伊索寓言《狼来了》。

一个放羊的孩子在山坡上看羊，觉得空闲无聊，便向村里大喊：“成功了！成功了！”村人赶来，才发现网络已经断了，返回值只是孩子随手填的零。

第二天，孩子又喊成功。村人问查询结果，孩子答：“零只羊。”问是不是空集合，答：“也许。”问是不是没有对象，答：“也许。”问是不是操作失败，孩子拍着终端道：“反正没有错误，错误都被我改成零了。”

村人渐渐不再看他的报信。到了狼真来时，警报查询恰好失败。孩子照例送回零，仓库照例撤销警报。羊群照例遭殃，只有监控图表一片安宁。

老村长气得胡子直抖，给孩子订了规矩：成功就带数，未找到就说未找到，失败就带具体错误。别让 `Option`、`Result` 和零值三家挤在一个门牌下。

孩子问：“那么传给上一层之后，狼是不是就走了？”村长说：“`?` 是传话，不是驱狼。上层还得决定重试、求援还是撤离。”

后来村里每个错误都实现了同一个 `Error` 接口，却仍保留各自的细节。狼又来时，孩子终于能说清是哪一路失败。村长颇欣慰，只叮嘱一句：“别为了报表好看，又给我统一成‘未知异常’。”

### 技术对照

Option 表达存在与否，Result 表达成功或失败。错误传播不等于已经恢复；unwrap、assert 和 panic 适合的前提需要由调用位置明确保证。
