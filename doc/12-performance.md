# LLVM AOT 跨语言性能

<!-- LANGUAGE NAVIGATION -->
[English](en/12-performance.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

当前程序版本为 **ChaLi 1.0.8**。本文只回答一个问题：ChaLi 的四元式交给 LLVM AOT（`-O3` + LTO）之后，同样的算法在 C、C++、Rust、Go、Java、Node、Lua、Python 面前处在什么位置。1.0.8 的编译器不再内嵌 VM 解释执行核，所以没有「VM 对比 AOT」这一节。

## 测什么

五个负载，都写成「同一份计算函数 + 同一个计时壳」的形式：

| 负载 | 算法 | 压的是什么 |
| --- | --- | --- |
| `int_chain` | 4,000,000 轮 `acc = (acc * 48271 + i) & 2147483647` | 整数依赖链，每轮都依赖上一轮 |
| `float_chain` | 4,000,000 轮浮点乘加 | FP 依赖链，考验寄存器分配 |
| `call` | 4,000,000 次极小函数调用 | 调用约定与内联判断 |
| `array` | 4,000,000 次 `a[acc & 15]` 读取 | 固定数组下标与边界 |
| `list` | 400,000 次 `push` 再遍历累乘 | 容器增长与堆分配 |

每个程序自己用单调时钟包住 `work()`，打印 5 行 `rep <纳秒>` 和一行 `sink <校验值>`。脚本只做构建、调度和中位数统计；**跨语言校验值必须一致**，否则直接判失败——这是「各语言确实算了同样的活」的唯一证据。

ChaLi 侧导出计算函数而不计时，计时壳用同一份 C 源码，并且**两边都用 LLVM `-O3`**（内核 `-O3 -flto=full`，C 壳 `-O3 -DNDEBUG`），避免壳的优化级别污染对照：

```powershell
chali aot work.chl --shared --out tmp/int_chain-kernel
clang -O3 -DNDEBUG driver.c int_chain-kernel.dll -lm -o int_chain-aot.exe
```

`driver.c` 就是 C 版本本身，只把被测函数换成 `#export` 出来的 `f_work`，计时函数和 `sink` 归并两边完全相同。

## 1.0.8 实测

Windows 10 x64、锐龙 12 逻辑核、外置 LLVM 变体（clang 23.1.4）；每配置 5 次进程 × 5 轮，单位毫秒：

| 配置 | int_chain | float_chain | call | array | list |
| --- | ---: | ---: | ---: | ---: | ---: |
| ChaLi 1.0.8（AOT，unchecked 导出） | 97.047 | 23.997 | 23.714 | 178.331 | 411.435 |
| ChaLi 1.0.8（AOT，checked `run`） | 100.273 | 23.973 | 24.447 | 188.494 | 444.205 |
| C（gcc -O2） | 4.322 | 1.302 | 0.869 | 7.145 | 0.904 |
| C++17（g++ -O2） | 4.330 | 1.303 | 0.903 | 6.998 | 0.990 |
| C++17（g++ -O3） | 4.348 | 1.303 | 0.917 | 7.082 | 0.856 |
| Rust（rustc -O） | 0.864 | 1.301 | 1.087 | 6.264 | 1.063 |
| Go（默认优化） | 4.657 | 1.546 | 1.047 | 7.252 | 1.553 |
| Java 22 `-Xint`（纯解释） | 64.815 | 15.827 | 29.804 | 71.175 | 13.884 |
| Java 22 `-Xbatch`（即时编译） | 5.049 | 1.313 | 1.088 | 6.322 | 1.575 |
| Node 26（V8 即时编译） | 72.138 | 1.301 | 16.097 | 60.173 | 8.973 |

## 怎么读这张表

**标量四件套在 18～28 倍之间。** 四个标量负载彼此接近，说明瓶颈不是某一个算子，而是每次四元式都要经过的那条通路：先把操作数从槽里读出来、算完再写回槽。C 的同类循环是「寄存器 + 一条乘加」，ChaLi 的循环里还夹着装载、存储和类型标记维护，LLVM 的 `-O3` 只能在这个形状上优化，不能替你换掉形状。

**`list` 单独贵一个数量级。** 40 万次 `push` 每次都要走运行时分配与值槽登记，遍历时再按元素读回，于是 400 毫秒量级——比 CPython 的内建 `list`（57.961）还慢 7 倍。这不是「LLVM 优化不够」，而是容器路径的调用密度高：`int_chain` 每轮只有一次乘加，`list` 每个元素要走完「分配 → 写值 → 增长回调」。

**checked 和 unchecked 差 0%～8%。** 边界与存活检查的绝对量在总成本里占比很小，因为真正的开销在槽访问与运行时调用上；`float_chain` 两者相同（23.973 对 23.997），`list` 因为每个元素都有检查点，差距最大（8%），但关掉检查也只从 444 毫秒降到 411 毫秒。把检查关掉救不了这五个负载，想提速只能改降低形状。

**Rust 在 `int_chain` 上比 C 快 5 倍**（0.864 对 4.322），是 LLVM 把这个递归定义的乘加循环重写成了更强的形式；同一台机器上 LLVM 也能这么干，前提是 IR 长得像循环，而不是像一串全局变量的读写。

**Java `-Xint` 与 Node 在 `int_chain` 上都快过 ChaLi AOT**（64.815、72.138 对 97.047）。这是本轮最该被记住的一条：解释器之所以快，是因为它的值留在寄存器／栈帧里，而当前的 AOT 产物让 LLVM 面对的是内存槽。`float_chain` 上 Node 与 C 持平（1.301），ChaLi 落后 18 倍；也就是说，槽访问的代价在浮点链上同样存在，不是整数专属。

## 读数的边界

本机偶有调度尖峰，长任务更容易被它打中：`int_chain` 的一格里有 25 个样本，ChaLi AOT 的最小值 91.038、中位 97.047、最大 131.7；C 在同一格里是 4.31～4.35，几乎不动。因此：

- 表里的倍数是**中位口径**，与 1.0.7 的报告可比；
- 想跨会话比较时对齐**最小值**：本轮最小口径的标量四项为 21.1、17.5、26.4、24.2，与上一轮报告的中位口径 21.1、17.7、26.3、25.2 一致，说明标量结论稳定；`list` 两轮分别是 507.3 与 392.7，差异来自 C 基线本身的抖动；
- `list` 的比值受 C 基线影响最大（C 的 `list` 本身只有 0.9 毫秒，抖动 10% 就会带动比值移动几十倍），看绝对值比看倍数可靠。

## 和 1.0.7 的关系

量级没有变：1.0.7 报告的是 21.9、17.4、26.0、24.7、492.5 倍，本轮 22.5、18.4、27.3、25.0、455.1 倍。`list` 从 492 降到 455，其余四项在噪声范围内。

1.0.8 真正变的是**编译期**：内部四元式优化与聚合优化整套删除，编译时间少了约 0.2 秒（2.79 秒对 3.01 秒，同一份源码、同一台机器），运行时间在 ±3.5% 内没有差别。原因就是上面那张表：运行时成本由降低形状决定，四元式层面的化简在 LLVM `-O3` 之后被完全覆盖，留着只是多花编译时间。因此 1.0.8 的编译器不再有 `CHALI_NO_OPT` 这类内部优化开关，只剩 5 个 AOT 快速路径开关（见[AOT 降低开关与计数](40-backend-ownership.md)）。

## 复现

```powershell
# 全部语言，5 次进程 × 5 轮
python benchmarks/perf/run.py --runs 5 --out benchmarks/results/aot-1.0.8

# 只跑 ChaLi 与原生对照
python benchmarks/perf/run.py --only chali-run,chali-aot,c,cpp-o3,rust,go
```

外置 LLVM 变体需要 clang 在 PATH 上（AOT 资产准备也用它）；Lua 需要先建宿主（首次会下载官方源码）：`python benchmarks/perf/build_lua.py`。原始样本、校验值、编译器 SHA256 与各工具版本写在 [1.0.8 基准报告](../benchmarks/results/aot-1.0.8/README.md) 与 [results.json](../benchmarks/results/aot-1.0.8/results.json)。

## 边界

- 单机单架构：Windows 10 x64、锐龙 12 逻辑核。没有 Linux 与 ARM 数据，不能外推到那些平台。
- 样本量：每格 25 个执行样本取中位数；进程启动、加载与 JIT 预热不在计时区内，Node 与 Java 的即时编译因此比「冷启动」看起来好。
- 负载很小：五个都是几百万次的微循环，反映的是**调用与访存密度**，不代表真实程序的混合负载。
- 表格里的「倍」是同一列除以 C 的中位数，不能跨列比较；Rust 比 C 快这类结果只对这份源码成立。
