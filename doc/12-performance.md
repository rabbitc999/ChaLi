# LLVM AOT 跨语言性能

<!-- LANGUAGE NAVIGATION -->
[English](en/12-performance.md) · **简体中文**
<!-- END LANGUAGE NAVIGATION -->

当前程序版本为 **ChaLi 1.0.8**。本文只回答一个问题：ChaLi 的四元式交给 LLVM AOT 之后，同样的算法在 C、C++、Rust、Go、Java、Node、Lua、Python 面前处在什么位置。1.0.8 的编译器不再内嵌 VM 解释执行核，所以没有「VM 对比 AOT」这一节。

## 测什么

五个负载，都写成「同一份计算函数 + 同一个计时壳」的形式：

| 负载 | 算法 | 压的是什么 |
| --- | --- | --- |
| `int_chain` | 4,000,000 轮 `acc = (acc * 48271 + i) & 2147483647` | 整数依赖链，每轮都依赖上一轮 |
| `float_chain` | 4,000,000 轮浮点乘加 | FP 依赖链，考验寄存器分配 |
| `call` | 4,000,000 次极小函数调用 | 调用约定与内联判断 |
| `array` | 4,000,000 次 `a[acc & 15]` 读取 | 固定数组下标与边界 |
| `list` | 400,000 次 `push` 再遍历累乘 | 容器增长与堆分配 |

每个程序自己用单调时钟包住 `work()`，打印 5 行 `rep <纳秒>` 和一行 `sink <校验值>`。脚本只做构建、调度和中位数统计；**跨语言校验值必须一致**，否则直接判失败——这是「各语言确实算了同样的活」的唯一证据。

ChaLi 侧导出计算函数而不计时：

```powershell
chali aot work.chl --shared --out tmp/int_chain-kernel
clang -O2 -DNDEBUG driver.c int_chain-kernel.dll -lm -o int_chain-aot.exe
```

`driver.c` 就是 C 版本本身，只把被测函数换成 `#export` 出来的 `f_work`，计时函数和 `sink` 归并两边完全相同。

## 1.0.8 实测

Windows x64、外置 LLVM 变体（clang 23.1.4，AOT 用 `-O3`）；每配置 5 次进程 × 5 轮，单位毫秒：

| 配置 | int_chain | float_chain | call | array | list |
| --- | ---: | ---: | ---: | ---: | ---: |
| ChaLi 1.0.8（AOT，unchecked 导出） | 91.306 | 23.047 | 22.746 | 174.833 | 398.753 |
| ChaLi 1.0.8（AOT，checked `run`） | 93.570 | 23.095 | 23.384 | 175.028 | 406.467 |
| C（gcc -O2） | 4.326 | 1.301 | 0.864 | 6.929 | 1.015 |
| C++17（g++ -O2） | 4.337 | 1.302 | 0.866 | 6.938 | 0.963 |
| C++17（g++ -O3） | 4.319 | 1.302 | 0.867 | 6.930 | 0.945 |
| Rust（rustc -O） | 0.864 | 1.300 | 1.089 | 6.263 | 0.945 |
| Go（默认优化） | 4.677 | 1.559 | 1.048 | 7.000 | 1.065 |
| Java 22 `-Xint`（纯解释） | 75.170 | 15.583 | 30.593 | 76.576 | 14.116 |
| Java 22 `-Xbatch`（即时编译） | 5.050 | 1.301 | 1.085 | 6.209 | 1.480 |
| Node 26（V8 即时编译） | 71.781 | 1.297 | 15.943 | 59.336 | 8.586 |
| Lua 5.5.1（官方 VM，默认 GC） | 31.094 | 6.472 | 16.940 | 41.805 | 12.402 |
| CPython 3.12（纯解释） | 320.579 | 30.111 | 117.605 | 205.620 | 55.950 |

| --- | ---: | ---: | ---: | ---: | ---: |
| ChaLi（unchecked 导出） | 21.1 | 17.7 | 26.3 | 25.2 | 392.7 |

| Lua 5.5.1 | 7.2 | 5.0 | 19.6 | 6.0 | 12.2 |
| CPython 3.12 | 74.1 | 23.2 | 136.1 | 29.7 | 55.1 |

## 怎么读这张表

**标量四件套在 17～26 倍之间。** 四个标量负载彼此接近，说明瓶颈不是某一个算子，而是每次四元式都要经过的那条通路：先把操作数从槽里读出来、算完再写回槽。C 的同类循环是「寄存器 + 一条乘加」，ChaLi 的循环里还夹着装载、存储和类型标记维护，LLVM 的 O3 只能在这个形状上优化，不能替你换掉形状。

**`list` 单独贵一个数量级。** 40 万次 `push` 每次都要走运行时分配与值槽登记，遍历时再按元素读回，于是 400 毫秒量级——比 CPython 的内建 `list`（55.950）还慢。这不是「LLVM 优化不够」，而是容器路径的调用密度高：`int_chain` 每轮只有一次乘加，`list` 每个元素要走完「分配 → 写值 → 增长回调」。

**checked 和 unchecked 差得很少（0.3%～2.2%）。** 边界与存活检查的绝对量在总成本里占比很小，因为真正的开销在槽访问与运行时调用上。这也意味着：把检查关掉救不了这五个负载，想提速只能改降低形状。

**Rust 在 `int_chain` 上比 C 快 5 倍**（0.864 对 4.326），是 LLVM 把这个递归定义的乘加循环重写成了更强的形式；同一台机器上 LLVM 也能这么干，前提是 IR 长得像循环，而不是像一串全局变量的读写。

**Java `-Xint` 在 `int_chain` 上比 ChaLi 快**（75.170 对 91.306），Node 也接近。这是本轮最该被记住的一条：解释器之所以快，是因为它的值留在寄存器／栈帧里，而当前的 AOT 产物让 LLVM 面对的是内存槽。

## 和 1.0.7 的关系

量级没有变：1.0.7 报告的 21.9、17.4、26.0、24.7、492.5 倍，本轮是 21.1、17.7、26.3、25.2、392.7 倍。`list` 从 492 降到 393，其余四项在噪声范围内。

1.0.8 真正变的是**编译期**：内部四元式优化与聚合优化整套删除，编译时间少了约 0.2 秒（2.79 秒对 3.01 秒，同一份源码、同一台机器），运行时间在 ±3.5% 内没有差别。原因就是上面那张表：运行时成本由降低形状决定，四元式层面的化简在 LLVM O3 之后被完全覆盖，留着只是多花编译时间。因此 1.0.8 的编译器不再有 `CHALI_NO_OPT` 这类内部优化开关，只剩 5 个 AOT 快速路径开关（见[AOT 降低开关与计数](40-backend-ownership.md)）。

## 复现

```powershell
# 全部语言，5 次进程 × 5 轮
python benchmarks/perf/run.py --runs 5 --out benchmarks/results/aot-1.0.8

# 只跑 ChaLi 与原生对照
python benchmarks/perf/run.py --only chali-run,chali-aot,c,cpp-o3,rust,go
```

Lua 需要先建宿主（首次会下载官方源码）：`python benchmarks/perf/build_lua.py`。原始样本、校验值、编译器 SHA256 与各工具版本写在 [1.0.8 基准报告](../benchmarks/results/aot-1.0.8/README.md) 与 [results.json](../benchmarks/results/aot-1.0.8/results.json)。

## 边界

- 单机单架构：Windows 10 x64、锐龙 12 逻辑核。没有 Linux 与 ARM 数据，不能外推到那些平台。
- 样本量：每格 25 个执行样本取中位数；进程启动、加载与 JIT 预热不在计时区内，Node 与 Java 的即时编译因此比「冷启动」看起来好。
- 负载很小：五个都是几百万次的微循环，反映的是**调用与访存密度**，不代表真实程序的混合负载。
- 表格里的「倍」是同一列除以 C 的中位数，不能跨列比较；Rust 比 C 快这类结果只对这份源码成立。
